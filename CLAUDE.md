# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the dev server
- `npm run build` — production build
- `npm run start` — run a production build

There is no linter or test suite configured in this repo — ESLint was deliberately removed (TypeScript's own diagnostics already cover unused-variable checks; the rest of the overlap wasn't worth keeping for this project).

## Architecture

Fehu is a personal finance tracker PWA: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4, Firebase (Firestore + Auth).

### Routing

Two route groups under `app/`: `(marketing)` (public, no auth) and `(app)` (the authenticated product). Route groups don't add a URL segment — `app/(app)/dashboard/page.tsx` is still just `/dashboard`. `app/(marketing)/page.tsx` renders the public landing page at `/` (see Marketing page below); `app/(app)/dashboard/page.tsx` renders the `Dashboard` at `/dashboard` (moved off `/` when the marketing page was added — see below for why), `app/(app)/budgets` is a real screen (see Budgets below), `app/(app)/insights` is a real screen (see Insights below), and `app/(app)/settings` has a real (if minimal) screen — see Auth model below. There is no Categories page or nav item — see Data layer below for why.

The root `app/layout.tsx` only wraps every page in `AuthProvider` (from `lib/use-auth.tsx`) — deliberately not `AppShell` or `CurrencyProvider`, since the marketing page needs neither (see Marketing page below for why it still wants `AuthProvider`, and Currency below for why `CurrencyProvider` moved). `app/(app)/layout.tsx` layers `CurrencyProvider` then `AppShell` (from `components/app-shell.tsx`, sidebar on desktop / burger-drawer on mobile, both anchored **left** — the mobile burger button lives at the top-left of the header to match, and the drawer slides in from the left) on top of that, scoped to just the authenticated routes, with nav items sourced from `lib/nav.ts`.

`components/wordmark.tsx`'s `Wordmark` uses `public/icons/f-mark.png` for the "F" — a transparent-background crop of the actual app icon's gold F glyph, extracted from `public/icons/launchericon-512x512.png` via a one-off Node/sharp script (hue-based matting: classify each pixel by `r - b` against the gold accent's own `r - b` spread, since the icon's background turned out to have a subtle gradient rather than one flat color, which broke a naive two-color linear projection first) — followed by "ehu" as plain text, so the wordmark reads "Fehu" with a real capital F rather than lowercase "fehu" plus a separate Unicode rune character (ᚠ) approximating one, which didn't match the actual icon's letterform. The mobile top bar deliberately has **no wordmark** — it only appears inside the drawer (matching the desktop sidebar's placement) — freeing the top-right of the mobile header for something else later, rather than a logo sitting there permanently. Extracted out of `app-shell.tsx` into its own file once `components/marketing/hero.tsx` needed the same glyph — was previously a private component only `AppShell` could see.

Nav `<Link>`s use `replace` (not the default push) — this is a tab-based nav, sibling tabs shouldn't have a browser back/forward relationship the way drill-down pages would. Without it, every tab switch pushed a new history entry, and on iOS this meant the edge-swipe-back gesture would navigate between tabs (with a native swipe-preview flash of whatever state — e.g. the mobile drawer being open — was on the page just before that history entry was recorded, since Safari snapshots for the preview). A CSS-only attempt at this (`touch-action: pan-y`) was tried first and didn't work — the gesture was legitimate, since a real history entry existed for it to go back to; `replace` removes the entry instead of trying to suppress the gesture.

### Marketing page (`app/(marketing)/page.tsx`)

Public, single-page landing site at `/` — no auth gate, since it lives outside `(app)`'s layout. Four sections in order: `components/marketing/hero.tsx` (wordmark, tagline, a CTA linking to `/dashboard` — labeled "Get started" or "Open Fehu" depending on `useAuth()`'s `user`, which is why the marketing page still needs `AuthProvider` from the root layout even though it skips `AppShell`), `components/marketing/features.tsx` (a static 4-card grid), `components/marketing/install-section.tsx` (see below), and `components/marketing/faq.tsx` (a plain accordion, one open item at a time via a single `openIndex` state — no library, consistent with the rest of the app avoiding extra dependencies for small custom UI). The CTA never embeds its own sign-in button — it just links to `/dashboard`, and `AppShell`'s existing sign-in gate handles the rest exactly as it already did before this page existed; duplicating the Google sign-in flow here would mean two places to keep in sync.

**Install prompting is genuinely different per platform, not just a styling choice** — `lib/use-install-prompt.ts` resolves to one of four states, checked in this order: `installed` (already running standalone — `display-mode: standalone` or iOS's `navigator.standalone`, in which case the section just links to `/dashboard` instead of prompting anything), `ios` (Safari on iPhone/iPad, detected via UA plus a `maxTouchPoints > 1` check since iPadOS has reported itself as a desktop Mac in the UA string since iPadOS 13 — Apple has never shipped a programmatic install API on iOS, so this state only ever gets manual Share-sheet instructions, never a real button), `installable` (a `beforeinstallprompt` event actually fired — Chromium only; the handler calls `preventDefault()`, stashes the event, and a real "Install app" button later calls `.prompt()` on it), and `other` (Firefox, or a Chromium browser that hasn't fired the event within a short timeout — generic "check your browser's menu" copy plus a link to web.dev's install guide, since there's no reliable way to know the exact menu wording across browsers). The timeout only sets a *fallback* — the `beforeinstallprompt` listener stays attached for the component's whole lifetime, so a late-firing event still upgrades `other` → `installable` rather than being missed.

`components/service-worker-registration.tsx` (mounted in the root `app/layout.tsx`, not `AppShell`) is what makes the `installable` state possible on this very page — Chromium won't fire `beforeinstallprompt` at all without an active service worker, and the registration effect used to live inside `AppShell`, which no longer mounts on `/`. Moved to the root specifically so a first-time visitor hitting the landing page can see a real install button, not just the authenticated app.

`app/manifest.ts`'s `start_url` points at `/dashboard`, not `/` — the manifest's install target is independent of what a browser visitor sees at the bare domain, and an installed home-screen icon launching into a marketing pitch instead of the app itself would be a worse experience than the two-tap "Add to Home Screen" flow it's trying to avoid.

### Auth model (`lib/use-auth.tsx`)

Auth state is a React Context (`AuthProvider`/`useAuth`), not a plain hook — this is deliberate: more than one component (the app shell, the dashboard) needs the same live auth state, and independent `onAuthStateChanged` listeners per hook call risk racing into separate sessions.

**⚠️ This auth system has been through a lot of iteration and is still a little rough around the edges.** Sign-in specifically went through several full redesigns (`signInWithPopup` → `signInWithRedirect` → back to popup with hand-built hang-detection → the current Google Identity Services approach below) chasing a mobile popup-hang bug — see git history / prior session notes for the full saga if something here seems inconsistent or overbuilt. The current approach is confirmed working on desktop (both `localhost` and the deployed domain); **not yet re-confirmed on mobile since the GIS switch** — that's the main thing still worth testing before trusting this area is fully settled.

Sign-in is mandatory and Google-only, currently implemented with **Google Identity Services (GIS)** — Google's own client-side library (loaded via `next/script` in `AppShell`) — rather than Firebase's own `signInWithPopup`/`signInWithRedirect`. GIS renders and manages its own button and popup lifecycle via `renderButton()`; our callback (passed to `google.accounts.id.initialize`) only ever fires with a real credential on success, so there's no "did the user close it" ambiguity to detect at all. The credential is exchanged for a Firebase session via `signInWithGoogleCredential` (`lib/use-auth.tsx`), which wraps `GoogleAuthProvider.credential(idToken)` + `signInWithCredential`.

**Deliberately not using GIS's One Tap `prompt()` flow** (tried it — a custom-styled button calling `prompt()`, with real cancel detection via `notification.getSkippedReason()`). It works, but depends on FedCM, which Chrome can silently suppress for a site after a user dismisses the prompt a few times — with no reliable way to detect or recover from that (Google's FedCM migration guide confirms the detail needed to distinguish this from an ordinary cancel, `getNotDisplayedReason()`, is being removed entirely for privacy reasons). `renderButton()`'s classic popup flow doesn't go through FedCM at all, so it isn't subject to this failure mode — chosen for that reason over the cosmetic benefit of a theme-matched custom button.

Prior to GIS: `signInWithPopup` worked but mobile browsers generally don't support true popup windows, breaking Firebase's own "is the popup still open" detection and leaving the sign-in UI hanging indefinitely if closed without completing. `signInWithRedirect` was tried as a fix but turned out broken more broadly — `getRedirectResult` silently resolving with nothing, reproduced on `localhost` *and* the real deployed domain, desktop *and* mobile, even in a clean Incognito profile (never fully root-caused, suspected browser third-party-storage policy) — and had an unwanted plain full-page-navigation feel besides. GIS was adopted specifically because it sidesteps this entire class of problem by design rather than needing another workaround.

`AuthProvider` exposes a `loading` flag (true until the first `onAuthStateChanged` callback fires) so `AppShell` can avoid flashing the sign-in screen while Firebase checks for an existing session; `AppShell` renders a full-screen sign-in gate whenever there's no `user`, and only renders the app (sidebar/nav/`children`) once signed in. There is deliberately no local-only/anonymous mode — every expense is tied to a real account from the first write, which avoids an earlier class of bugs around orphaned anonymous data and popup/credential-linking edge cases.

`AuthProvider` also exposes `deleteAccount`: deletes all of the user's Firestore docs first — both `transactions` and `budgets` (batched, while still authenticated — Firestore's rules require `request.auth.uid == userId`), then calls `deleteUser` on the Firebase Auth account. There's no top bar or account banner anymore — "Delete account" lives in `app/settings/page.tsx`, gated behind `components/delete-account-dialog.tsx`, a custom modal that requires typing the word "delete" before the delete button enables (replaced an earlier native-`confirm()` version — deliberately heavier-handed than a single confirm click since this is irreversible). "Log out" lives at the bottom of the nav stack in `AppShell` (both the desktop sidebar and the mobile drawer), separated from the regular nav items by a border, rather than in a top bar. Note account deletion doesn't revoke Google's own OAuth consent grant for the app (that's tracked independently by Google, not Firebase) — signing in again with the same Google account afterward won't re-show the permissions screen, since Google still remembers the prior authorization.

Firestore security rules (managed in the Firebase console, not checked into this repo) restrict each user's data to `request.auth.uid == userId`, currently scoped to `/users/{userId}/expenses/**` — **this needs updating manually in the Firebase console** to `/users/{userId}/transactions/**` plus new rules for `/users/{userId}/budgets/**` and `/users/{userId}/settings/**` (the latter added for `lib/use-currency.tsx`), none of which is tracked in this repo. The collection was renamed from `expenses` to `transactions` once income tracking was added, done as a clean rename with no migration path — safe only because there's no real user data yet (pre-launch); this would need an actual migration once the app has real users.

### Data layer

There is **no fixed category list anymore** (no `CategoryId`, no Categories page/nav item) — budgets themselves are the categorization. Each budget is a user-defined `{ name, amount, cadence }`; an expense optionally references one by `budgetId`. This replaced an earlier design (still worth knowing about if it resurfaces in old notes/git history) where categories were a hard-coded 8-item enum (Food, Transit, Bills, …) and budgets were per-category spending caps keyed by that enum — deliberately dropped in favor of the current, fully user-defined model.

- `lib/firebase.ts` — initializes the Firebase app, `auth`, and `db`. Firestore uses `persistentLocalCache` for offline read/write support (writes queue locally and sync when back online).
- `app/manifest.ts` — the web app manifest (`name`, `icons`, `display: standalone`, theme colors matching the app's dark background). Icons live in `public/icons/` at six sizes (48–512px); each file's actual pixel dimensions were verified to match its filename/declaration. `app/layout.tsx`'s `metadata.icons.apple` separately points at the 192×192 icon for iOS's home-screen icon — iOS Safari doesn't reliably read the manifest's icons the way Chrome/Android does, so without this it falls back to an inconsistent or blurry screenshot-based icon.
- `public/service-worker.js` — service worker covering *app-shell* offline support (separate from Firestore's data-level offline support above): network-first for same-origin GET requests, falling back to the cache when offline; deliberately ignores cross-origin requests (so it never intercepts Firestore/Google API calls) and non-GET requests. Registered from `components/app-shell.tsx`, production builds only (`npm run dev` never registers it, so cached code doesn't go stale while iterating). `AppShell` also tracks `navigator.onLine` to show a "no internet connection" message on the sign-in screen instead of a sign-in button that's guaranteed to fail offline.
- `lib/use-transactions.ts` — realtime Firestore hook (`onSnapshot`) scoped to `/users/{uid}/transactions`, ordered by date, exposing `transactions` plus `addTransaction`/`updateTransaction`/`deleteTransaction`. `updateTransaction` also strips the `budgetId` field via `deleteField()` when editing a transaction's type to `"income"`, since income transactions never reference a budget and it would otherwise linger as stale data on the doc.
- `lib/use-budgets.ts` — realtime, full-CRUD Firestore hook scoped to `/users/{uid}/budgets` (one doc per budget, auto-generated id — not keyed by anything fixed), exposing `budgets` plus `addBudget`/`updateBudget`/`deleteBudget`. `deleteBudget` queries `/users/{uid}/transactions` for any doc referencing the budget's id and strips their `budgetId` via `deleteField()` in the same batch as the budget's own deletion — otherwise those transactions would be left with a `budgetId` pointing at a doc that no longer exists (a real bug that shipped briefly: the transactions stayed queryable and correct as standalone expenses, but the dangling reference itself was never cleaned up). They still end up as valid, standalone expense records, just no longer linked to any budget.
- `lib/data.ts` — **not** a data source (the old hard-coded expense array was removed once Firestore was wired up). It's shared types (`Transaction` — a discriminated union on `type: "expense" | "income"`, only the expense variant carries an optional `budgetId`; `Budget` — `{ id, name, amount, cadence: "monthly" | "one-time" }`) and formatting helpers (`formatCurrency(value, currency?)`, `relativeDay` — handles both past *and future* dates ("tomorrow", "in N days"), needed once `add-transaction-sheet.tsx` let the date be anything, not always today — `currentMonthLabel`, `todayISO`/`toLocalISODate`). `formatCurrency`'s `currency` param defaults to `DEFAULT_CURRENCY` ("EUR") but every real call site in the app passes the user's actual selection explicitly — see Currency below. **Above €1,000,000 it abbreviates** ("€1.2M", "€1.5B", "€2.5T") instead of printing every digit — a large sum (a total, a running one-time budget, …) could otherwise overflow a fixed-width display like the dashboard's hero "Net" figure; truncating with an ellipsis was ruled out since hiding digits off a money figure is actively misleading. `components/amount-input.tsx` separately caps what a user can actually *type* at 999,999,999.99 (`MAX_AMOUNT`) — but that only bounds a single amount; a *sum* (Net, Budgets' Total, a one-time budget's running total) isn't bounded by it at all, since there's no limit on how many transactions or budgets can exist, so `formatCurrency` has to scale past billions too, not just the one tier a capped single entry could reach. Its `UNITS` ladder (M/B/T) handles the boundary case where rounding would otherwise print "1000M" instead of bumping to the next tier up, at every step, not just M→B. T is the top tier, with nowhere left to bump to — past that (a sum reaching into the quadrillions, unrealistic but not impossible given sums are unbounded), `formatCurrency` prints a plain `"-"` instead of a wrong number like "1000T", signaling "too large to display" rather than showing something misleading. Below €1M, full comma-grouped precision as always.

### Currency (`lib/currencies.ts`, `lib/use-currency.tsx`)

`lib/currencies.ts` is a short list of major currencies — USD, EUR, JPY, GBP (`CurrencyCode`, `currencies`, `currencyMap`, `DEFAULT_CURRENCY` = "EUR") plus a synthetic `"OTHER"` entry — each with a **hardcoded** `symbol` ($, €, ¥, £). Deliberately not delegated to `Intl.NumberFormat`'s own currency-symbol data — ICU doesn't have a clean glyph for every currency (Swiss Franc, for one, just renders as the literal code "CHF" under `style: "currency"`), so this always shows exactly the symbol given here. The list went through a few rounds of curation before landing here — first tried keeping only currencies with a "pure" single-glyph symbol, then tried collapsing symbol-sharing currencies (USD/CAD/AUD all sharing `$`, etc.) down to one generic representative each, then briefly expanded to 8 named currencies with hand-picked distinguishing symbols (A$, C$, Fr., 元) — before settling on this smaller, symbol-only set. USD's label is "Dollar" rather than "US Dollar" (no other dollar-family currency is in the list to disambiguate from); EUR/JPY/GBP keep their normal names. `formatCurrency` (`lib/data.ts`) never uses `Intl`'s `style: "currency"` at all, only `style: "decimal"` for the number, with `currencyMap[currency].symbol` prepended manually (sign handled separately so negatives read `-$12.34`, not `$-12.34`). `"OTHER"`'s symbol is `""`, so this naturally prints a bare number with no prefix for it — no special-casing needed in `formatCurrency` itself, though `components/currency-picker-sheet.tsx` does skip the `(symbol)` suffix for it (every other row is `"{label} ({symbol})"`) since empty parens would look broken. `lib/use-currency.tsx` is a `CurrencyProvider`/`useCurrency()` Context (same reasoning as `AuthProvider`: many components format money, so one shared subscription beats each mounting its own listener on the same doc), scoped to `/users/{uid}/settings/preferences` → `{ currency }`, wrapped around `AppShell` in `app/(app)/layout.tsx` (inside `AuthProvider`, since it needs `useAuth()`'s `user`) — scoped to just the authenticated route group rather than the root layout, since the public marketing page never formats money and doesn't need its own listener on that doc. Every component that calls `formatCurrency` or shows a currency symbol calls `useCurrency()` itself rather than receiving `currency` as a threaded-down prop — that includes `dashboard.tsx`'s local `BudgetCard` — consistent with how `useAuth()` is already called directly wherever needed rather than prop-drilled.

Changed from Settings (`app/settings/page.tsx`) via `components/currency-picker-sheet.tsx` — a bottom sheet listing all `currencies` (name + symbol in parens, current selection checked — including "Other", which renders as literal empty parens `()` rather than being hidden, showing there's genuinely nothing there instead of omitting the row's usual structure), opened by a small button showing just the current symbol with **no text fallback** — selecting "Other" leaves the button showing nothing but its chevron, which is the point (the word "Other" never appears on the trigger, only inside the sheet). That trigger button and the "Delete account" button in the row below share the same `min-w-20` (a floor, not a fixed width — either can still grow past it if its content ever needs more room) plus identical padding/text-size/centering, so the two rows' right-hand controls line up; the floor still matters since a bare `$` is much narrower than other symbols, and letting the pill shrink-to-fit made it visibly resize as the selection changed. **Deliberately not a native `<select>`** — an earlier version used one, but a native select's open dropdown can't be restyled away from the browser/OS's own default appearance (white background, system font, no dark-theme support), which looked out of place; a native `<select>` also needs `text-base` (16px) to avoid iOS Safari's focus-zoom, which made it visually mismatched in height against its sibling row's `text-xs` "Delete" button. The sheet-based picker sidesteps both problems — full control over styling since it's just app markup, and the trigger is a plain button that can stay `text-xs` like everything else in that row, since a button doesn't trigger the zoom behavior a real form field does. The amount inputs in `add-transaction-sheet.tsx` and `add-budget-sheet.tsx` show `currencyMap[currency].symbol` instead of a hardcoded `€` (see the Budgets section below for how that's positioned).

### Shared UI pieces

- `components/sheet.tsx` — **the app's one modal/bottom-sheet shell.** Every dialog in the app (`add-transaction-sheet.tsx`, `add-budget-sheet.tsx`, `budget-detail-sheet.tsx`, `currency-picker-sheet.tsx`, `confirm-dialog.tsx`, `delete-account-dialog.tsx`) renders through `<Sheet>` rather than hand-rolling its own overlay — it owns the backdrop (click to close), the slide-up rounded container, the drag-handle bar, Escape-to-close, and body-scroll-lock while open; each caller supplies only its header/body/footer as children. This exists because those six used to each hand-roll the same markup independently, and it quietly drifted: only the two add/edit sheets had Escape-to-close and scroll-lock, the other four had neither (though all six already closed on backdrop click, since that part happened to get copy-pasted consistently). Configurable per caller: `maxWidth` (`max-w-md` default, `max-w-sm` for the shorter confirm/picker dialogs), `scrollable` (adds `max-h-[80vh] flex flex-col` for a sheet with a long list body — `budget-detail-sheet.tsx`, `currency-picker-sheet.tsx`), `role` (`"alertdialog"` for confirm/destructive dialogs vs the default `"dialog"`), and `zIndex` (`confirm-dialog.tsx` uses `z-[60]` since it can stack on top of an already-open sheet, e.g. deleting a transaction from within `budget-detail-sheet.tsx`).
- `components/sheet-header.tsx` — the title + close (X) button row every sheet uses right after `<Sheet>`'s opening tag. Extracted once four sheets had it duplicated with a stray inconsistency (two used `mb-5`, two used `mb-4`) — this pins it to one value. Takes a `capitalize` flag for `add-transaction-sheet.tsx`'s heading specifically, which is built as `` `${verb} ${txType}` `` (e.g. "Add expense") and needs the second word capitalized too.
- `components/amount-input.tsx` — the big centered euro-sign-plus-number field shared by `add-transaction-sheet.tsx` and `add-budget-sheet.tsx` (was duplicated identically, comment included, before being pulled out). Reads the current currency itself via `useCurrency()` rather than taking it as a prop. `value`/`onChange` stay a plain digit string with no commas — callers (and `Number.parseFloat` elsewhere) never see formatting — but what's actually shown in the `<input>` is live thousands-grouped (typing "100000" displays "100,000") via an internal `groupThousands()`, with the cursor repositioned by counting digits rather than characters (`countDigits`/`positionAfterDigits`) so inserting/deleting a comma-adjacent digit doesn't jump the cursor to a character index that's shifted by the comma itself. On blur, the value is normalized to exactly 2 decimals (`parsed.toFixed(2)`) if it parses, so "100000" settles into "100,000.00" once the user moves on rather than only while a `.` has actually been typed. While typing, decimal digits are capped at 2 (currency doesn't have a third) and a second "." is deduped rather than left in — `Number.parseFloat` silently truncates at a second "." rather than rejecting it, which wasn't obvious from the UI.

The input is a **fixed `w-[11ch]`, sized for realistic amounts** ("999,999.99" is 10 characters), **not** `MAX_AMOUNT`'s technical ceiling ("999,999,999.99") — this went through a few wrong turns worth knowing about if it comes up again: sizing the box for the true maximum kept a normal amount like €45.00 looking off-center, since centered text only fills part of a box that wide; resizing the box to fit content on every keystroke (via the native `size` attribute) fixed that but made the whole row visibly jitter left while typing, since re-centering on every character shifts existing digits left while the matching growth on the right (needed to keep it centered) has nothing visible to show for it. A fixed, modest box sidesteps both: **correct centering for every realistic amount**, and a genuinely huge one (approaching `MAX_AMOUNT`) just falls back to the input's own contained horizontal scroll — a deliberate tradeoff, not an oversight, since nobody's actually logging a near-billion-euro personal expense. The symbol and the amount are positioned **independently of each other**, not as one adjacent unit — the symbol is `absolute` at `left-0` of the full-width root, aligning flush with every other label in the sheet ("Description", "Budget", …), while the amount is centered on its own within that same full width via a nested `flex justify-center`, unaffected by the symbol's width or position. (An earlier version anchored the symbol relative to the input itself — `right-full` — so the pair moved together and the symbol ended up wherever the centered input happened to land, not aligned with the rest of the sheet; that positioning was also what an even earlier mobile-overflow bug traced back to, though this version is safe regardless since the box is fixed and modest rather than growing toward the container's own width for large numbers.)

The input itself is a **fixed** `w-[16ch]` (comfortably fits "999,999,999.99", the longest possible value at `MAX_AMOUNT`, 15 characters — with a `min-w-0 max-w-full` backstop, since a flex item's default `min-width: auto` can otherwise refuse to shrink below an explicit width and push the row past the sheet's edge on the narrowest viewports), not resized per keystroke. A version that resized the input to fit its content on every keystroke (via the native `size` attribute) caused the whole row to visibly jitter left while typing — the row re-centers on every character, so existing digits shift left each time while the matching growth on the right has nothing visible to show for it. **Nothing about this layout changes while typing now, only the text content does**, so there's nothing left to jitter. `text-left`, not centered, is what actually closes the gap between the symbol and a short number: centered text in a wide fixed box sits in the box's middle regardless of how much of it the number actually needs, while left-aligned text always lands immediately next to the symbol.

`Sheet` also tracks a module-level `openStack` (ids from `useId()`, pushed/popped as each instance's `open` prop goes true/false) so that when two sheets are stacked, **Escape only closes the topmost one** — the same as clicking outside already does, but for a different reason: a backdrop click only ever reaches the front sheet naturally (its full-screen backdrop physically covers whatever's behind it), while Escape is a single global `keydown` that every currently-open sheet's listener receives regardless of stacking, so without this check the *back* sheet would close first on the first Escape press (a real bug that shipped briefly) rather than the front one.
- `components/confirm-dialog.tsx` — the app's only confirm pattern for destructive-but-not-catastrophic actions (deleting a single transaction, deleting a budget). Built once and reused rather than duplicating the modal markup at each call site (each caller owns its own `open`/target state and passes in a title + description); native `confirm()`/`alert()` are avoided everywhere — they look and behave inconsistently on mobile and don't match the app's design. `components/delete-account-dialog.tsx` (Settings) is deliberately **not** built on `ConfirmDialog` — account deletion needed a heavier, type-"delete"-to-confirm flow, different enough from a plain yes/no that reusing it would have meant bolting extra props onto a shared component for one special case. Both still go through `Sheet` for their actual shell, just with different content.
- `components/empty-state.tsx` — the shared "nothing here yet" box (monochrome card, bordered, a colored icon in a circle, instructional text below). Used by `app/insights/page.tsx` (no transactions yet), `app/budgets/page.tsx`'s empty list, and `components/dashboard.tsx`'s empty-budgets state.

### Dashboard (`components/dashboard.tsx`)

Built around net worth rather than a spending list: header (a plain "Welcome back!" greeting — an earlier version showed the month/year here instead, and a small avatar circle with the user's initial before that, removed as clutter; the month/year label moved down to sit above the budget cards instead, replacing what used to say "Budgets" there), then one row holding "Net" (this month's income minus expenses, the hero number, `items-end`-aligned against the two smaller figures beside it) with "Spent" and "Earned" to its right — all three in one horizontal row, each with its label stacked above its amount, not the whole trio stacked as separate rows, via `justify-between` with only two flex children — Net flush to the row's start, and a `Spent`+`Earned` sub-group (its own `gap-5`) flush to the end — rather than a fixed `gap` across all three, which spread `Spent` toward the middle instead of keeping it paired with `Earned`. Below that, stacked budget cards (one per budget from `lib/use-budgets.ts`, largest amount first) under a plain month/year label (via `currentMonthLabel()`) — **not a link**; navigation to `/budgets` happens only through the main nav and, when the list is empty, the empty state's inline link (see below), not a second in-page control that would duplicate it. There is deliberately **no transaction list on the dashboard itself** — tapping a budget card opens `components/budget-detail-sheet.tsx`, a bottom sheet listing that budget's matching transactions, each with edit (pencil) and delete (trash) icons. A budget card's progress bar is `--accent` normally; if `spent > amount` it switches to `--danger` and fills to 100% regardless of how far over. The empty-budgets state uses `components/empty-state.tsx`; only the word "Budgets" inside the sentence is a link, styled bold white (`font-bold text-foreground`) with **no underline** — clickability is signaled instead by `hover:scale-110` (the word grows slightly on hover), since underline-on-hover was deliberately dropped in favor of that.

"Spent" is computed differently depending on a budget's `cadence`, via `lib/data.ts`'s `budgetSpending()` (shared with `app/insights/page.tsx` — see Insights below, which needs the exact same per-budget numbers rather than a second, possibly-diverging calculation) — **monthly** budgets sum only this calendar month's matching expenses (resets every month); **one-time** budgets sum *all* matching expenses ever (a running total that never resets, since a one-time budget represents a fixed target rather than a recurring monthly cap). The same distinction carries into `budget-detail-sheet.tsx`'s transaction list — current month only for monthly budgets, all-time for one-time ones, since `budgetSpending()` returns each budget's already-cadence-scoped `transactions` alongside its `spent` total.

Opening the add form is responsive: mobile keeps the floating FAB (fixed bottom-right, `md:hidden` — thumb-reachable, the standard mobile convention), while desktop hides that and shows an inline circular button next to the month label instead (`hidden ... md:flex`, `size-11`, solid `bg-accent`, just a `Plus` icon, no text) — a fixed corner-anchored circle read as disconnected from the rest of the page on a wide desktop viewport, so desktop moves it inline near the header, in the same spot Budgets' "Add budget" button occupies on its own page. Deliberately **not** styled as a pill-with-text like that button, though — this is the app's primary action, the same weight as the FAB itself, so it keeps the FAB's own circle-with-plus shape rather than reading as a sibling of a page-scoped secondary action. Both trigger the same `components/add-transaction-sheet.tsx`, which has an Expense/Income toggle at the top — **only when adding**; when editing (`editing` prop set) the toggle is gone with nothing in its place (an earlier version showed a static "Expense"/"Income" label there instead, but that read as redundant clutter — the amount and description are enough context), since a transaction's type can't be changed after creation (switching an expense to income would need to somehow reattach or strand its `budgetId`, which is confusing either way — simplest to just not allow it). For Expense, budget pills are generated dynamically from the user's actual budgets (`budgets` prop, passed down from `components/dashboard.tsx`'s `useBudgets`) — tapping one sets `budgetId`. **A budget is required for an expense** (the submit button stays disabled without one — an unbudgeted expense doesn't show up on any budget card, which read as data quietly going missing rather than a valid state); if the user has no budgets yet, the picker shows "Add a budget first to log an expense" instead of pills. **Description is optional** — only amount (and budget, for an expense) are required; if left blank, the stored `title` falls back to `"-"` rather than an empty string, so nothing renders as a blank row wherever `title` is displayed later. The same sheet component handles both adding and editing: an `editing: Transaction | null` prop pre-fills the form and switches `onAdd` to `onUpdate` on submit; `components/dashboard.tsx` opens it in edit mode from the budget detail sheet's pencil icon.

The **Date** field is a small standalone gold pill (`border-accent/40 text-accent`, no separate label — the pill itself, showing `relativeDay(date)` — "today"/"tomorrow"/"in N days"/a short date — is self-explanatory) that opens `components/date-picker-sheet.tsx`, a from-scratch calendar grid (Monday-first week, matching the `en-IE` locale used elsewhere) rather than a native `<input type="date">` — same reasoning as the currency picker: a native date input's popup can't be restyled to match the dark theme. Defaults to today (`lib/data.ts`'s `todayISO()`) for a new transaction, or the transaction's existing date when editing. `todayISO()`/`toLocalISODate()` build the ISO string from local year/month/day rather than `Date#toISOString()` (UTC-based, which silently shifts the date near midnight in timezones ahead of or behind UTC) — `lib/use-transactions.ts`'s `addTransaction` used to auto-stamp `new Date().toISOString().slice(0, 10)` itself, which had exactly that latent bug; the date is now just a normal field on `NewTransaction` that the sheet supplies, defaulting via the correct local-date helper.

`components/budget-detail-sheet.tsx` also shows the same spent/limit text + progress bar treatment as the dashboard's budget cards, right below the title — it sums the `transactions` prop it's given (already scoped to the right window by the caller) rather than taking a separate `spent` prop, since that sum is the same number the card already computed.

### Budgets (`app/budgets/page.tsx`)

Where budgets are actually created/edited/deleted (the dashboard only reads and displays them). Below the title/add-button header row, a "Total" stat (sum of every budget's `amount`, regardless of cadence) uses the exact same label-then-hero-number treatment as the dashboard's "Net" (`text-xs text-detail` label, `mb-0.5`, then `text-[34px]` for the amount) for visual consistency between the two. A quiet, outline-style "Add budget" button (`border-accent/40 text-accent`, not a solid fill — deliberately less loud than the dashboard's solid-accent FAB) opens `components/add-budget-sheet.tsx`, which asks for amount, name, and cadence ("Monthly budget" / "One-time budget"). The cadence control is a small binary switch (`role="switch"`, a 36×20px pill track with a sliding thumb — the thumb needs an explicit `left-0.5` anchor plus a `translate-x` for the slide, **not** just a bare `translate-x` with no `left` set, which left it relying on the browser's implicit static-position fallback and made it render outside the track), not a wide segmented-pill toggle like Expense/Income in the transaction sheet — deliberately kept quiet/low-emphasis since it's a secondary setting, not the primary decision on the form the way expense-vs-income is. Doubles as the edit form via an `editing: Budget | null` prop, same pattern as `add-transaction-sheet.tsx`. Both this sheet's and `add-transaction-sheet.tsx`'s big amount input show the currency symbol (`currencyMap[currency].symbol` — was a hardcoded `€` before multi-currency support) via `components/amount-input.tsx` — see that entry above for how the symbol stays centered against the number without risking rendering outside the sheet on mobile. The budgets list itself is sorted largest-to-smallest by amount; each row is a plain `py-3` list item divided by `border-b border-border` — **deliberately no card border/rounding** here (a version that borrowed the dashboard budget cards' bordered shell, to force matching height/width between the two screens, was tried and reverted; the two are allowed to look different, this list doesn't need to visually match the dashboard's cards). Each row has the name, cadence, amount, and edit/delete icons (delete goes through `components/confirm-dialog.tsx`), plus a thin fixed-accent-color line underneath every row — **not** proportional to amount, purely decorative, identical on every row regardless of size (an earlier version varied its width by amount, which read as a meter and was confusing since nothing about it was actually fillable — dropped for exactly that reason). Empty state uses `components/empty-state.tsx` with the `Wallet` icon (same icon as the Budgets nav item).

### Insights (`app/insights/page.tsx`)

Two sections, both reading from the same `useTransactions`/`useBudgets` data the rest of the app already uses (deliberately no data-retention/history-trimming work yet — see below), and both driven by the same period pills (1M/3M/6M/1Y/All) at the top of the page — per the usual dataviz rule that a filter scopes *everything* below it, so the chart and the ranked list always agree on what window they're describing:

1. **Chart** (`components/insights-chart.tsx`) — monthly spend vs. income, as two line series over the selected period (filtered client-side from `lib/data.ts`'s `monthlyTotals()`). Spend is the primary series (gold `--accent`, with a faded gradient area fill under it — an SVG `<linearGradient>` from ~22%-opacity gold at the line down to fully transparent at the baseline, via `useId()` for a collision-safe per-instance gradient id; a flat low-opacity fill was tried first and read as "plain," not faded); income is a plain 2px line at 70% opacity in the app's own `--foreground` white/off-white — deliberately *not* a second brand hue: this is a primary-vs-context pairing (spend is the story, income is there for scale), not two equally-weighted categorical identities, so it borrows the existing text-foreground token rather than adding a new brand color. Deliberately two *lines* on one shared axis, not a dual-axis chart, since spend and income are both currency amounts (a second y-axis is the #1 chart-design mistake for exactly this "two measures, same unit" case). The chart's `<svg>` uses `w-full` for a responsive width, and its CSS `aspect-ratio` is set to match the viewBox's own aspect ratio (`${WIDTH} / ${HEIGHT}`) rather than a fixed pixel height — an earlier version paired `w-full` with a fixed `height: 150px`, which almost never matches the viewBox's aspect ratio (300:116) exactly, so the browser's default `preserveAspectRatio="xMidYMid meet"` scaled the whole viewBox down to fit *inside* that mismatched box and letterboxed it — centered, with invisible empty margins on both sides that had nothing to do with any internal padding. `aspect-ratio` fixes that generally, without the distortion a blunter `preserveAspectRatio="none"` fix would have caused (that stretches non-uniformly, visibly squashing the circular end-markers into ellipses whenever the container's width doesn't happen to match). `PAD_LEFT`/`PAD_RIGHT` (14 units each) exist purely so the x-axis month labels — 3-letter, `textAnchor="middle"`, sitting exactly at the first/last plotted x position — have enough room not to clip past the SVG's own edges; the value is sized for that specific text, not chosen for visual spacing.

**No numeric y-axis at all** — the 3 gridlines (0 / half / a "nice" rounded max via `niceCeiling()`) are purely visual guides with no value labels next to them; an earlier version showed the rounded values, removed on request. They're dotted (`strokeDasharray="2,3"`), not solid — a deliberate style call overriding the dataviz skill's usual "gridlines are solid hairlines" default, since this is a specific aesthetic choice for this chart rather than an oversight. The x-axis still gets month labels, thinned to roughly 6 when there'd otherwise be too many to fit (`labelStep = Math.ceil(points.length / 6)`, always keeping the most recent month's label even if it'd otherwise be skipped by the stride). **No hover/crosshair interaction** — an earlier version tracked pointer position with a crosshair line and a tooltip card; both were removed (the tooltip first, once the page already had a Spent/Earned figure making it redundant; the whole hover mechanism shortly after, on request, to keep the chart non-interactive for now). What's left is a static end-of-line marker (one dot per series) fixed at the most recent point, not tied to any pointer state.
2. **Budgets, ranked** — no section label (an earlier "Budgets, ranked" heading was removed as unnecessary — the ranked list is visually self-explanatory right under the chart). Every budget with at least one matching expense **inside the selected period**, sorted by that period's spend, highest first, via `lib/data.ts`'s `budgetSpendingInPeriod(budgets, transactions, period)` — deliberately *not* the cadence-aware `budgetSpending()` the Dashboard uses (which is always "this calendar month" for monthly budgets, "ever" for one-time ones, with no period concept at all). Insights instead scopes strictly to the period's actual date range regardless of a budget's own cadence, and **drops any budget with zero matching transactions in that window** — a one-time budget funded 4 months ago won't appear under 1M or 3M, only once the selected period reaches back far enough to include that transaction. This was a deliberate correction: an earlier version reused the Dashboard's cadence-based figure directly, which meant a one-time budget's all-time total kept showing up under every period pill including 1M even with zero activity that month — confusing next to a chart and hero numbers that *do* change with the period. Tapping a row still reuses `budget-detail-sheet.tsx` unchanged, passed that row's period-scoped `transactions`.

Each row also gets a thin gold line underneath (`h-[3px] bg-accent`, same visual language as `app/budgets/page.tsx`'s per-row line) — but unlike that one, which is explicitly fixed-width and decorative (see Budgets above), this one's width is proportional to `spent / maxSpent` across the currently ranked set, turning it into a simple comparative meter so the largest-to-smallest gap between budgets reads at a glance. The two pages showing the same visual element with different meaning is intentional, not an inconsistency — Budgets' list is a management view (nothing there is "fillable"), Insights' list is specifically about relative comparison.

`lib/data.ts`'s `budgetSpending()` (Dashboard's cadence-aware, period-less version) and `budgetSpendingInPeriod()` (Insights' period-scoped version) share a private `periodStartMonth()` helper with `monthlyTotals()` for computing a period's start month, but are otherwise separate functions with different semantics — don't try to unify them further; the period-vs-cadence distinction is the point, not an accident of two similar-looking functions.

**No transaction-editing UI beyond what `budget-detail-sheet.tsx` already provides** — income transactions still have no edit/delete affordance anywhere in the app (an earlier draft of this page added a full "all transactions" list specifically to close that gap; removed per explicit feedback that Insights shouldn't duplicate that surface for now). Worth revisiting later, just not part of this page.

**Demo mode for local testing** (`lib/dummy-data.ts`): visiting `/insights?demo=1` in `next dev` (gated on `process.env.NODE_ENV !== "production"`, so this is a no-op in any production build regardless of the query string) swaps the page's `transactions`/`budgets` for `generateDummyData()`'s output — a seeded-random ~1 year of realistic income/expense activity across 4 monthly budgets and 2 one-time ones, generated relative to the real current date (not hardcoded ISO strings) so "this month" cadence logic exercises correctly no matter when it's run. The current calendar month is deliberately forced net-negative (an extra "Car repair" expense sized to whatever it takes to push that month's spend past its income, computed from the month's own accumulated totals rather than a guessed constant, since the ordinary random expenses alone weren't reliably enough to push it negative on their own) — this exists specifically to exercise the negative-net UI path (Dashboard's "Net" figure going negative, formatted with a leading `-`) without waiting for a real account to actually go over budget. Edit/delete become no-ops in demo mode rather than attempting real Firestore writes against fake document ids. Still requires signing in normally first — demo mode only swaps the *data* Insights renders, not the auth gate.

**Explicitly deferred**: nothing here bounds how much history loads — `useTransactions`' `onSnapshot` still fetches a user's entire transaction collection, same as before this page existed. That's a real scaling concern (Firestore's free-tier read quota is project-wide, not per-user, and an unbounded per-user history multiplies fast), but the plan is to build Insights first, then simulate several years of data for a realistic user count and measure whether some form of history compaction is actually feasible before investing in it — possibly landing as a paid-tier gate instead if it isn't. Don't add consolidation/archiving logic speculatively; it's an open, explicitly-postponed decision, not a missing feature.

### Styling

Tailwind v4 theme tokens are defined in `app/globals.css` via CSS variables + `@theme inline`: `background`, `foreground`, `accent`, `danger`, `detail`, `muted`, `border`, `border-strong`, `card`, `surface`, `radius-card`. Use these token names (`bg-card`, `text-detail`, etc.) rather than raw hex values or ad hoc colors — the one exception is `components/insights-chart.tsx`'s actual SVG `stroke`/`fill` attributes, which use plain hex constants (matching `--accent`'s and `--foreground`'s real values) instead of `var(--accent)`, since CSS custom property resolution inside SVG presentation attributes isn't worth the cross-browser risk for a color that already lives as a real Tailwind token for every other (HTML) use.

Any `<input>`/`<textarea>`/`<select>` needs `text-base` (16px) or larger — iOS Safari auto-zooms the page on focus if a form field's font size is under 16px. There's no global guard against this (a blanket CSS rule would also shrink the intentionally-large amount input in `add-transaction-sheet.tsx`), so it has to be applied per-field.

### Path alias

`@/*` maps to the repo root (see `tsconfig.json`), e.g. `@/lib/data`, `@/components/dashboard`.

### Environment

Firebase web config lives in `.env.local` as `NEXT_PUBLIC_FIREBASE_*` variables (gitignored, required for `lib/firebase.ts` to initialize). `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is the OAuth Web client ID Firebase auto-created for the Google sign-in provider (same value visible in Firebase console → Authentication → Sign-in method → Google, or Google Cloud Console → Credentials) — required by `AppShell`'s Google Identity Services setup.

**Setup gotcha:** GIS separately requires every origin it'll run from (`http://localhost:3000`, the deployed Vercel domain, etc.) to be listed under that same OAuth Client ID's **"Authorized JavaScript origins"** in Google Cloud Console (APIs & Services → Credentials — a direct link like `https://console.cloud.google.com/apis/credentials?project=<firebase-project-id>` gets there fastest). This is a *different* setting from Firebase's own "Authorized domains" list (Authentication → Settings) — missing it produces a real Google-hosted "Access blocked: Authorisation error" page, not a console warning, so it's easy to mistake for something more exotic if you don't know to look here first.
