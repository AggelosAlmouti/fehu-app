# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the dev server
- `npm run build` — production build
- `npm run start` — run a production build

There is no linter or test suite configured in this repo — ESLint was deliberately removed (TypeScript's own diagnostics already cover unused-variable checks; the rest of the overlap wasn't worth keeping for this project).

## Architecture

Fehu is a personal finance tracker PWA: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4, Firebase (Firestore + Auth).

### Routing

Two route groups under `app/`: `(marketing)` (public, no auth) and `(app)` (the authenticated product). Route groups don't add a URL segment — `app/(app)/dashboard/page.tsx` is still just `/dashboard`. `app/(marketing)/page.tsx` renders the public landing page at `/` (see Marketing page below); `app/(app)/dashboard/page.tsx` renders the `Dashboard` at `/dashboard` (moved off `/` when the marketing page was added — see below for why), `app/(app)/budgets` is a real screen (see Budgets below), `app/(app)/insights` is a real screen (see Insights below), and `app/(app)/settings` has a real (if minimal) screen — see Auth model below. There is no Categories page or nav item — see Data layer below for why.

The root `app/layout.tsx` wraps every page in `AuthProvider` (from `lib/use-auth.tsx`) — deliberately not `AppShell` or `CurrencyProvider`, since the marketing page needs neither. The marketing page doesn't actually use `AuthProvider` either at this point (it did briefly, for an auth-aware CTA label that's since been simplified away — see Marketing page below); it stays at the root only because `(app)` routes need it, not because `/` does. `app/(app)/layout.tsx` layers `CurrencyProvider` then `AppShell` (from `components/app-shell.tsx`, sidebar on desktop / burger-drawer on mobile, both anchored **left** — the mobile burger button lives at the top-left of the header to match, and the drawer slides in from the left) on top of that, scoped to just the authenticated routes, with nav items sourced from `lib/nav.ts`.

`components/wordmark.tsx`'s `Wordmark` uses `public/icons/f-mark.png` for the "F" — a transparent-background crop of the actual app icon's gold F glyph, extracted from `public/icons/launchericon-512x512.png` via a one-off Node/sharp script (hue-based matting: classify each pixel by `r - b` against the gold accent's own `r - b` spread, since the icon's background turned out to have a subtle gradient rather than one flat color, which broke a naive two-color linear projection first) — followed by "ehu" as plain text, so the wordmark reads "Fehu" with a real capital F rather than lowercase "fehu" plus a separate Unicode rune character (ᚠ) approximating one, which didn't match the actual icon's letterform. The mobile top bar deliberately has **no wordmark** — it only appears inside the drawer (matching the desktop sidebar's placement) — freeing the top-right of the mobile header for something else later, rather than a logo sitting there permanently. Extracted out of `app-shell.tsx` into its own file once the marketing page's hero needed the same glyph — was previously a private component only `AppShell` could see.

Nav `<Link>`s use `replace` (not the default push) — this is a tab-based nav, sibling tabs shouldn't have a browser back/forward relationship the way drill-down pages would. Without it, every tab switch pushed a new history entry, and on iOS this meant the edge-swipe-back gesture would navigate between tabs (with a native swipe-preview flash of whatever state — e.g. the mobile drawer being open — was on the page just before that history entry was recorded, since Safari snapshots for the preview). A CSS-only attempt at this (`touch-action: pan-y`) was tried first and didn't work — the gesture was legitimate, since a real history entry existed for it to go back to; `replace` removes the entry instead of trying to suppress the gesture.

### Marketing page (`app/(marketing)/page.tsx`)

Public, single-page landing site at `/` — no auth gate, since it lives outside `(app)`'s layout. Everything — hero, features, FAQ — lives directly in `app/(marketing)/page.tsx` as one file, not split into `components/marketing/*` pieces the way an earlier version had it: none of the three sections are used anywhere else, so the split was buying file-count overhead with no reuse to justify it (unlike `sheet.tsx`, `empty-state.tsx`, or `wordmark.tsx`, which earn their own files by being used in multiple places — see Shared UI pieces below). Three sections in order: hero (wordmark, tagline, a CTA linking to `/dashboard`), features (a static 6-card grid — PWA, simplicity, real-time sync, offline, low friction, insights; deliberately not the full feature list, e.g. multi-currency isn't advertised here even though it exists in the app, since this is meant to sell the handful of things that actually differentiate the product rather than enumerate everything it does), and FAQ (a plain accordion, one open item at a time via a single `openIndex` state — no library, consistent with the rest of the app avoiding extra dependencies for small custom UI). Its questions are pricing, data privacy, "what is a PWA" (syncs in real time between devices, no app store needed — the answer a reader unfamiliar with the term actually needs, not a technical definition), account requirements, and whether installing is mandatory — deliberately not an exhaustive FAQ; a standalone "does it work offline" question that used to sit here was dropped, not merged elsewhere — offline support is still real (see Data layer below) and still shown as its own card in Features above, just no longer duplicated as FAQ copy too.

**Install prompting is split across two pages on purpose, not duplicated carelessly** — `lib/use-install-prompt.ts` resolves to one of six states: `checking` (initial, pre-detection — renders nothing), `installed` (already running standalone — `display-mode: standalone` or iOS's `navigator.standalone`; the install UI disappears entirely and sign-in becomes the only content, since you're already in the app), `already-installed` (installed, but currently open in a browser tab rather than the standalone app — set when `promptInstall()` resolves `"accepted"`, when the `appinstalled` event fires, or on a later visit from the `localStorage` flag those two write; needed because a Chromium PWA *stops* firing `beforeinstallprompt` once installed, so without it a returning tab visit falls through to the generic `other` box — a real bug that was hit. The flag self-heals: `beforeinstallprompt` firing again, i.e. after an uninstall, clears it. There's no web API to launch an installed PWA from a page, so this state just shows a one-line "Fehu is already installed." note), `installable` (a `beforeinstallprompt` event actually fired — Chromium only; the handler calls `preventDefault()`, stashes the event, and a real "Install app" button later calls `.prompt()` on it — a `"dismissed"` outcome drops back to `installable` so the button stays), `ios` (Safari on iPhone/iPad — UA plus a `maxTouchPoints > 1` check since iPadOS has reported itself as a desktop Mac in the UA string since iPadOS 13 — **and** desktop Safari on macOS, matched as a `Macintosh` UA that's Safari-not-Chrome/Firefox/Edge with zero touch points; Apple ships no programmatic install API on any of these, so this state gets an **icon-bulleted instruction box** — Share → "Add to Home Screen" → "Add" — never a button, and it's deliberately the loudest of the install treatments since these users are the most likely to not know what "add to home screen" means), and `other` (everything else — Firefox, a Chromium browser that hasn't fired the event within a short timeout, or anything unrecognized — the **same icon-bulleted box design** as `ios` with a generic menu path, closing with a plain "see your browser's guide for installing PWAs" line and, deliberately, **no link** — we can't verify the right destination for an unknown browser, so we don't guess). The timeout only sets a *fallback* — the `beforeinstallprompt` listener stays attached for the component's whole lifetime, so a late-firing event still upgrades `other` → `installable` rather than being missed. Firefox was briefly its own state with browser-specific copy (it has no native install path at all — confirmed against MDN's own docs, only a third-party extension) but that was deliberately collapsed back into `other`: only Chrome and Safari get dedicated treatment. **Dev-only test hook:** in `next dev` (gated on `process.env.NODE_ENV !== "production"`, a no-op in any production build), a `?install=ios|other|installable|already-installed|installed` query param on the sign-in gate forces that state so the install UI can be checked without the matching device/browser — e.g. `/dashboard?install=ios`. `installable` forced this way has no real `deferredPrompt` behind it, so the "Install app" button renders but doesn't do anything.

**The marketing page itself makes no install decisions at all.** The hero has exactly one CTA, always linking to `/dashboard`, labeled "Get the app" — copy on this page (headline, subtext, CTA label) has gone through several hand-edited iterations and should be treated as deliberately tuned, not something to "clean up" back to an earlier phrasing found in git history. The CTA doesn't check `useInstallPrompt()` at all, not even for the `installable` (Chromium) case, even though that one's technically safe to show anywhere — an earlier version did show a second "Install app" button here, but it was simplified back to one CTA to keep this page from having async, detection-driven UI at all; the real decision happens one click later, uniformly, on the sign-in gate. That's also a correctness requirement, not just a simplification: `components/install-section.tsx` (used on the sign-in gate — see Auth model below) renders `ios`/`other` manual-instruction states that must never appear on `/`. Reason: `beforeinstallprompt`'s `.prompt()` is browser-managed and always installs to the manifest's `start_url` regardless of which page triggered it, so it *would* be safe here — but iOS's manual "Add to Home Screen" has a real, documented history of just bookmarking whatever URL happens to be loaded rather than reliably honoring the manifest's `start_url`. Showing those instructions from `/` risks recreating the exact stale-`start_url` bug already hit once (see below) — an icon that opens the marketing pitch forever instead of the app. `components/install-section.tsx` only ever renders on the sign-in gate specifically because that page *is* `/dashboard`, the correct install target, so a manual "Add to Home Screen" from there can't get it wrong regardless of how iOS actually resolves it.

`components/service-worker-registration.tsx` (mounted in the root `app/layout.tsx`, not `AppShell`) is what makes the `installable` state possible on this very page — Chromium won't fire `beforeinstallprompt` at all without an active service worker, and the registration effect used to live inside `AppShell`, which no longer mounts on `/`. Moved to the root specifically so a first-time visitor hitting the landing page can see a real install button, not just the authenticated app.

`app/manifest.ts`'s `start_url` points at `/dashboard`, not `/` — the manifest's install target is independent of what a browser visitor sees at the bare domain, and an installed home-screen icon launching into a marketing pitch instead of the app itself would be a worse experience than the two-tap "Add to Home Screen" flow it's trying to avoid.

**The manifest link is global on purpose, even though that means Chrome's own install icon can appear on the marketing page too** — this was a deliberate reversal worth understanding if it comes up again. An earlier version went to real lengths to prevent that: dropping Next's `app/manifest.ts` special-file convention (which injects `<link rel="manifest">` into *every* page regardless of which segment the file lives in — moving the file or scoping `metadata.manifest` to `app/(app)/layout.tsx` alone didn't stop it) in favor of a hand-rolled route handler at `app/manifest.webmanifest/route.ts`, specifically so the link would only render on `(app)` routes. That was reverted back to the plain `app/manifest.ts` file (global, standard, gets `MetadataRoute.Manifest` type-checking for free) once it became clear the thing it was preventing was never actually a correctness bug: Chrome's manifest-driven install — whether triggered by the browser's own address-bar icon or a `beforeinstallprompt`-backed button — always resolves `start_url` correctly regardless of which page triggered it. The *only* real correctness risk was iOS's manual "Add to Home Screen," which does just bookmark whatever's currently loaded — and that's fully handled independently of manifest scoping, simply by never showing our own iOS instructions anywhere except the sign-in gate (see above). So the worst case now is a Chrome user occasionally installing straight from `/` via the browser's own UI, bypassing our guided copy — which still lands correctly on `/dashboard`, just without having seen it first. Accepted trade: a simpler, standard, better-typed manifest file over a non-obvious workaround that a future pass over this code could easily "clean up" back to the special file without realizing it was deliberately structured otherwise.

**Manifest changes don't retroactively apply to an already-installed icon** — this bit us once already: `start_url` was briefly `/` before this page existed, and changing it in code + redeploying does nothing for anyone who installed during that window, since the OS snapshots the manifest (start_url, icons, everything) at install time. iOS never meaningfully re-checks it afterward; Android/Chrome's WebAPK re-check is backgrounded and not instant. The fix for a stale install is always the same: remove it from the home screen and re-add it. Don't mistake this for a routing bug if it comes up again — verify by checking the live `/manifest.webmanifest` response directly before assuming the code is wrong.

### Auth model (`lib/use-auth.tsx`)

Auth state is a React Context (`AuthProvider`/`useAuth`), not a plain hook — this is deliberate: more than one component (the app shell, the dashboard) needs the same live auth state, and independent `onAuthStateChanged` listeners per hook call risk racing into separate sessions.

**⚠️ This auth system has been through a lot of iteration and is still a little rough around the edges.** Sign-in specifically went through several full redesigns (`signInWithPopup` → `signInWithRedirect` → back to popup with hand-built hang-detection → the current Google Identity Services approach below) chasing a mobile popup-hang bug — see git history / prior session notes for the full saga if something here seems inconsistent or overbuilt. The current approach is confirmed working on desktop (both `localhost` and the deployed domain); **not yet re-confirmed on mobile since the GIS switch** — that's the main thing still worth testing before trusting this area is fully settled.

Sign-in is mandatory and Google-only, currently implemented with **Google Identity Services (GIS)** — Google's own client-side library (loaded via `next/script` in `AppShell`) — rather than Firebase's own `signInWithPopup`/`signInWithRedirect`. GIS renders and manages its own button and popup lifecycle via `renderButton()`; our callback (passed to `google.accounts.id.initialize`) only ever fires with a real credential on success, so there's no "did the user close it" ambiguity to detect at all. The credential is exchanged for a Firebase session via `signInWithGoogleCredential` (`lib/use-auth.tsx`), which wraps `GoogleAuthProvider.credential(idToken)` + `signInWithCredential`.

**`lib/firebase.ts` deliberately uses `initializeAuth()` instead of the more common `getAuth()`, omitting `popupRedirectResolver` entirely — found via the same slow-connection testing as the service worker work above.** `getAuth(app)` (no args) is sugar for `initializeAuth(app, { popupRedirectResolver: browserPopupRedirectResolver, persistence: [...] })`, and `browserPopupRedirectResolver` has a `_shouldInitProactively` flag that's `true` on mobile browsers, Safari, and iOS specifically (see the SDK's own source, `@firebase/auth/dist/esm/*.js` — `BrowserPopupRedirectResolver`) — on those, it proactively opens a cross-origin `gapi.iframes` helper (loading `https://apis.google.com/js/api.js`) as soon as Auth starts up, purely so it's ready in case a popup/redirect result ever needs handling, regardless of whether the app calls one. Since this app moved entirely to GIS + `signInWithCredential` above and never calls `signInWithPopup`/`signInWithRedirect`, that resolver was configured but never actually used for anything — yet the proactive iframe/gapi load still happened unconditionally on every mobile/Safari page load, and was a real, confirmed contributor to the app hanging on slow mobile connections (traced via DevTools' Network tab during a real hang: an `apis.google.com/js/api.js` request, initiated by Firebase's own SDK, taking multiple seconds on throttled 3G — separate from and in addition to the service worker gaps above, which were fixed first and ruled out via the same investigation before this was found). `initializeAuth(app, { persistence: [...] })` without `popupRedirectResolver` skips that entirely, with no functional loss since nothing here uses popup/redirect. Falls back to `getAuth(app)` in a `catch` for the dev-hot-reload case — Auth can't be `initializeAuth()`'d twice for the same app, and `getAuth()` short-circuits to the already-initialized (already resolver-less) instance rather than re-initializing with its own defaults, so the fallback doesn't undo this.

**Even after that fix, a second Firebase Auth network dependency remained — confirmed by direct timing instrumentation (a temporary `console.log` bracketing `AuthProvider`'s effect mount and its first `onAuthStateChanged` fire), not just Network-tab correlation: a ~2.1s gap (mount at ~422ms, callback at ~2563ms) under 3G throttle.** Restoring an *already signed-in* session makes its own network call (`accounts:lookup` against `identitytoolkit.googleapis.com`, from `@firebase/auth`'s `PersistenceUserManager`/`AuthStateManager` internals) to validate the persisted session before the SDK will fire the first `onAuthStateChanged` — this has no configurable timeout, isn't something `initializeAuth`'s options can skip, and isn't safe to patch inside the SDK. Since `AppShell` gated its *entire* render (not just Firestore-backed data, the static sidebar/nav chrome too) behind `loading` from that callback, a slow-but-connected network meant a stark blank `<div>` for as long as that call took — the same "waits as long as it needs" failure mode as the original service-worker bug, just relocated one layer deeper, into Firebase Auth's SDK rather than our own fetch handling.

**Fixed with an app-level optimistic-render layer in `lib/use-auth.tsx`, independent of Firebase's own timing** — since the network call itself can't be bounded or bypassed: every time `onAuthStateChanged` fires, the confirmed `{ uid, email }` (or `null` on sign-out) is mirrored into `localStorage` (`fehu-last-user`) — a synchronous, instant, local write. On the *next* load, that value seeds `optimisticUser` — **but read inside a mount-only `useEffect`, not a `useState(readOptimisticUser)` lazy initializer** (a real bug, since fixed: a lazy initializer runs during render on both the server, which has no `localStorage` and always got `null`, and the client's first hydration pass, which does — so any returning signed-in visitor hit a genuine hydration mismatch, `AppShell` disagreeing with itself about `hasPriorSession` between server and client). `optimisticUser` now starts `null` on every render path, matching the server exactly, and the effect corrects it one client-only re-render later — still well ahead of `onAuthStateChanged`'s own network round-trip. The context exposes `effectiveUser = user ?? optimisticUser` (the real Firebase `User` once confirmed, the remembered stand-in until then) alongside a `hasPriorSession` flag. `AppShell`'s gate changed from a single `if (loading)` to two checks: blank only when `loading && !hasPriorSession` (nothing to show yet — first-ever visit, or genuinely signed out last time); the sign-in gate only when `!loading && !user` (Firebase has spoken and there's truly no one signed in). Everything else — `loading && hasPriorSession` included — renders the real app shell immediately. If the optimistic guess turns out wrong (the session was actually revoked server-side), `loading` flipping to `false` with `user` still `null` falls through to the sign-in gate on the next render; this is the accepted trade discussed when this was decided — a brief window where the shell shows before correcting itself, in exchange for never blank-screening a returning user on a slow connection. Every `useAuth().user` call site that only ever read `.uid`/`.email` (confirmed by grepping for all `user.`/`user?.` property access across the codebase before making this change — nothing reads any other `User` method or field) was switched to `effectiveUser` instead — `components/dashboard.tsx`, `app/(app)/budgets/page.tsx`, `app/(app)/insights/page.tsx`, and `lib/use-currency.tsx` — so the Firestore-backed hooks they feed (`useTransactions`, `useBudgets`, the currency listener) start their `onSnapshot` subscriptions immediately instead of waiting for `user` to resolve first. **This turned out to only fix the shell, not the data itself** — see the `getDocsFromCache` entry further down for why `onSnapshot` still doesn't actually deliver anything faster this way, and why that's a separate, harder problem left unfixed for now. `AppShell`'s own two `user?.email` displays (sidebar and mobile drawer) switched to `effectiveUser?.email` for the same reason. The real `user` value is still exposed and still what the sign-in-gate branch and the GIS-button-setup effect key off — nothing here weakens the actual security boundary, which is enforced by Firestore's rules checking the real `request.auth.uid` regardless of what the client optimistically renders.

**A real bug, now fixed**: navigating away from the sign-in gate and back (e.g. `/dashboard` → back to `/` → forward to `/dashboard` again) used to leave the Google button permanently missing. Cause: `next/script` only fires its `onLoad` callback the *first* time a given `src` loads in the browser session — `AppShell` unmounts and remounts across that navigation (different route groups, no shared layout), and the second mount's `<Script onLoad={...}>` never fires again since the script was already loaded, so `googleScriptLoaded` never became `true` and `renderButton()` was never called. Fixed with a second effect that checks `window.google` directly on mount and sets the flag immediately if the script already loaded in an earlier mount, rather than relying solely on `onLoad` ever firing again.

**Deliberately not using GIS's One Tap `prompt()` flow** (tried it — a custom-styled button calling `prompt()`, with real cancel detection via `notification.getSkippedReason()`). It works, but depends on FedCM, which Chrome can silently suppress for a site after a user dismisses the prompt a few times — with no reliable way to detect or recover from that (Google's FedCM migration guide confirms the detail needed to distinguish this from an ordinary cancel, `getNotDisplayedReason()`, is being removed entirely for privacy reasons). `renderButton()`'s classic popup flow doesn't go through FedCM at all, so it isn't subject to this failure mode — chosen for that reason over the cosmetic benefit of a theme-matched custom button.

Prior to GIS: `signInWithPopup` worked but mobile browsers generally don't support true popup windows, breaking Firebase's own "is the popup still open" detection and leaving the sign-in UI hanging indefinitely if closed without completing. `signInWithRedirect` was tried as a fix but turned out broken more broadly — `getRedirectResult` silently resolving with nothing, reproduced on `localhost` *and* the real deployed domain, desktop *and* mobile, even in a clean Incognito profile (never fully root-caused, suspected browser third-party-storage policy) — and had an unwanted plain full-page-navigation feel besides. GIS was adopted specifically because it sidesteps this entire class of problem by design rather than needing another workaround.

`AuthProvider` exposes a `loading` flag (true until the first `onAuthStateChanged` callback fires) so `AppShell` can avoid flashing the sign-in screen while Firebase checks for an existing session; `AppShell` renders a full-screen sign-in gate whenever there's no `user`, and only renders the app (sidebar/nav/`children`) once signed in. **That gate is deliberately just two affordances — an install control and the Google button, separated by an "or" divider — with no page headings or marketing copy.** `useInstallPrompt()` is called in `AppShell` itself (not inside `InstallSection`, which is purely presentational, taking `status`/`onInstall` as props) so the gate can pick the install control above the sign-in button per the six-state list in Marketing page above: a content-width "Install app" button (`installable`), an icon-bulleted instruction box (`ios` / `other`), a one-line "already installed" note (`already-installed`), or nothing (`installed`/`checking`). The "— or —" divider shows only when there's a real install action or instruction competing with sign-in — `installable`/`ios`/`other`, not `already-installed`/`installed`/`checking`. The GIS button itself is `size: "medium"` (down from `"large"` — it should read as the quieter of the two options when an install control is on offer) and is *additionally* dimmed to `opacity-70` only when a real "Install app" button is competing with it — not for `ios`/`other`/`already-installed`, where it's the only actionable control. The `#google-signin-button` node stays mounted in one fixed position whenever online — only its className toggles, and the divider/`InstallSection` above it are separate sibling slots that don't recreate the node — so `renderButton()`'s effect never has to re-fire on an install-status change (a remounted button node is the documented cause of the button-goes-missing bug below). It's still the one screen every signed-out visitor reaches regardless of entry point (the marketing page's own CTA already skips straight to `/dashboard`), so it's a more reliable place to offer installing than the marketing page alone (see Marketing page above for the full writeup, including why the iOS/other-browser instructions specifically *must* live here and not on `/`).

**Install is also offered from the Settings page** (`app/(app)/settings/page.tsx`) — for someone who signed in "to check it out" and then wants to install without signing out again to reach the gate. It's the **first row of the settings card**, styled exactly like the Currency / Delete account rows (label + description, a `min-w-20` outline pill on the right) rather than the gate's standalone treatment — the row is shown only for `installable`/`ios`/`other` (nothing for `already-installed`/`installed`/`checking`). the pill always says "Install" and acts by state — `installable` calls `promptInstall()` directly (no chevron, like Delete account); `ios`/`other` opens a `Sheet` whose body is `<InstallInstructions>` (with a chevron, like Currency). That component (`components/install-instructions.tsx`) is the shared step list — the icon bullets plus, for `other`, the "see your browser's guide" line — used both by the Settings sheet and inside `InstallSection`'s gate box, so the wording lives in one place. `useInstallPrompt()` is just called a second time in `Settings` rather than lifted to a context (it's cheap — DOM listeners plus a `localStorage` read, not a Firestore subscription — and only two call sites want it; `AppShell`'s own instance is idle when signed in since the gate isn't rendered). Note the `ios` instructions on `/settings` are the one spot that bends the "iOS manual instructions only ever appear at `/dashboard`" rule from Marketing page above — accepted because the manifest link is injected on every page and modern iOS (16.4+) honors `start_url`, but it's the thing to re-check if an installed-from-Settings icon ever opens the wrong screen. There is deliberately no local-only/anonymous mode — every expense is tied to a real account from the first write, which avoids an earlier class of bugs around orphaned anonymous data and popup/credential-linking edge cases.

`AuthProvider` also exposes `deleteAccount`: deletes all of the user's Firestore docs first — both `transactions` and `budgets` (batched, while still authenticated — Firestore's rules require `request.auth.uid == userId`), then calls `deleteUser` on the Firebase Auth account. There's no top bar or account banner anymore — "Delete account" lives in `app/(app)/settings/page.tsx`, gated behind `components/delete-account-dialog.tsx`, a custom modal that requires typing the word "delete" before the delete button enables (replaced an earlier native-`confirm()` version — deliberately heavier-handed than a single confirm click since this is irreversible). "Log out" lives at the bottom of the nav stack in `AppShell` (both the desktop sidebar and the mobile drawer), separated from the regular nav items by a border, rather than in a top bar. Note account deletion doesn't revoke Google's own OAuth consent grant for the app (that's tracked independently by Google, not Firebase) — signing in again with the same Google account afterward won't re-show the permissions screen, since Google still remembers the prior authorization.

Firestore security rules (managed in the Firebase console, not checked into this repo) restrict each user's data to `request.auth.uid == userId`, currently scoped to `/users/{userId}/expenses/**` — **this needs updating manually in the Firebase console** to `/users/{userId}/transactions/**` plus new rules for `/users/{userId}/budgets/**` and `/users/{userId}/settings/**` (the latter added for `lib/use-currency.tsx`), none of which is tracked in this repo. The collection was renamed from `expenses` to `transactions` once income tracking was added, done as a clean rename with no migration path — safe only because there's no real user data yet (pre-launch); this would need an actual migration once the app has real users.

### Data layer

There is **no fixed category list anymore** (no `CategoryId`, no Categories page/nav item) — budgets themselves are the categorization. Each budget is a user-defined `{ name, amount, cadence }`; an expense optionally references one by `budgetId`. This replaced an earlier design (still worth knowing about if it resurfaces in old notes/git history) where categories were a hard-coded 8-item enum (Food, Transit, Bills, …) and budgets were per-category spending caps keyed by that enum — deliberately dropped in favor of the current, fully user-defined model.

- `lib/firebase.ts` — initializes the Firebase app, `auth`, and `db`. Firestore uses `persistentLocalCache` for offline read/write support (writes queue locally and sync when back online).
- `app/manifest.ts` — the web app manifest (`name`, `icons`, `display: standalone`, theme colors matching the app's dark background). Icons live in `public/icons/` at six sizes (48–512px); each file's actual pixel dimensions were verified to match its filename/declaration. `app/layout.tsx`'s `metadata.icons.apple` separately points at the 192×192 icon for iOS's home-screen icon — iOS Safari doesn't reliably read the manifest's icons the way Chrome/Android does, so without this it falls back to an inconsistent or blurry screenshot-based icon.
- `public/service-worker.js` — service worker covering *app-shell* offline support (separate from Firestore's data-level offline support above): **cache-first** for same-origin GET requests — a cached response is served immediately if one exists, with the network request still made in the background to refresh the cache for next time; only a request with nothing cached yet actually waits on the network. This was network-first (fetch, falling back to cache only on rejection) until it became clear that's a real bug on a slow/flaky connection rather than just an offline one: `fetch()` doesn't reject when the network is merely slow, so the app would hang waiting on a response that was going to arrive eventually instead of falling back to the already-available cache — the opposite of what a "load fast" PWA shell should do. Cache-first trades one thing away (a same-session app-shell update can take an extra reload to show up, since the stale-but-cached version is what gets served while the refresh happens quietly underneath) for consistently-fast opens regardless of connection quality, which matters more here than always-latest shell code. Deliberately ignores cross-origin requests (so it never intercepts Firestore/Google API calls) and non-GET requests. Registered from `components/service-worker-registration.tsx` (mounted in the root `app/layout.tsx` — see Marketing page above for why it lives there and not in `AppShell`), production builds only (`npm run dev` never registers it, so cached code doesn't go stale while iterating). **Once registered, it outlives the build that registered it** — a real debugging trap, hit once already: if `npm run build && npm run start` is ever run against `localhost:3000` (even just once), the browser keeps that service worker active indefinitely, and it'll keep cache-first-serving that old production snapshot to `next dev` on the same origin afterward too, since service worker lifecycle is per-origin, not per-process — every subsequent code change looks like it's silently not taking effect, no matter how many times the dev server or browser is restarted, because the worker never re-registers itself to update (registration only happens on a production build's load, which was the one time it ran). Fix is DevTools → Application → Service Workers → Unregister, plus clearing site data to drop the stale `fehu-cache-v2` cache too — not a code bug, don't go looking for one in the app if this happens again. `AppShell` also tracks `navigator.onLine` to show a "no internet connection" message on the sign-in screen instead of a sign-in button that's guaranteed to fail offline.

  **A gap in the plain cache-first version above, found via real-device testing on slow-but-connected wifi (not offline) — fixed in-house, no Workbox/service-worker library pulled in:** a page's own first-ever load is never controlled by a service worker that's installing during that same load, so "a repeat visit" from the user's perspective can still be the *first SW-controlled* request for every asset on a given device — the fetch handler had never run for them before, so nothing had actually been cached yet despite it not being the user's first visit to the page. On a bad connection that meant sitting on a blank screen (well, just the background color — the HTML shell painted fine, but the JS needed to hydrate it was still an uncached, un-timed-out `fetch()` away) for as long as the connection stayed bad. Fixed by precaching every real route (`PRECACHE_ROUTES` — mirrors `lib/nav.ts`'s hrefs plus `/`) at `install` time: fetching each route's HTML up front, parsing out the `/_next/static/...` asset URLs it references, and caching all of it before the new service worker ever activates, so the first SW-controlled load of any route is guaranteed a full cache hit rather than depending on an earlier visit having incidentally warmed it. A plain timeout on the runtime fetch (abort and fail after N seconds) was tried and deliberately dropped — picking a magic number to paper over a possible miss was the wrong fix; making misses actually rare via precaching is. `/_next/static/*` responses are also content-hashed by filename and can never go stale, so a cache hit for one skips the background revalidation fetch entirely (`isImmutableAsset()`) — unlike the mutable HTML document, there's nothing to refresh, and skipping it means one less thing competing for bandwidth on a bad connection. `CACHE_NAME` bumped to `fehu-cache-v2` alongside this so `activate` evicts the old cache-first-only cache rather than leaving it to linger unused under the same name.
- `lib/use-transactions.ts` — realtime Firestore hook (`onSnapshot`) scoped to `/users/{uid}/transactions`, ordered by date, exposing `transactions` plus `addTransaction`/`updateTransaction`/`deleteTransaction`. `updateTransaction` also strips the `budgetId` field via `deleteField()` when editing a transaction's type to `"income"`, since income transactions never reference a budget and it would otherwise linger as stale data on the doc.
- `lib/use-budgets.ts` — realtime, full-CRUD Firestore hook scoped to `/users/{uid}/budgets` (one doc per budget, auto-generated id — not keyed by anything fixed), exposing `budgets` plus `addBudget`/`updateBudget`/`deleteBudget`. `deleteBudget` queries `/users/{uid}/transactions` for any doc referencing the budget's id and strips their `budgetId` via `deleteField()` in the same batch as the budget's own deletion — otherwise those transactions would be left with a `budgetId` pointing at a doc that no longer exists (a real bug that shipped briefly: the transactions stayed queryable and correct as standalone expenses, but the dangling reference itself was never cleaned up). They still end up as valid, standalone expense records, just no longer linked to any budget.

  **`getDocsFromCache`/`getDocFromCache` were tried and reverted as a fix for slow-to-appear budgets/transactions/currency under 3G — don't re-attempt this, it doesn't work, and here's why.** After the `effectiveUser` optimistic-auth fix above, the app shell rendered instantly, but its *data* still took as long to appear as everything else had before — direct timing showed `onSnapshot`'s first delivery taking ~2.2s under 3G throttle *even when it came back `snapshot.metadata.fromCache: true`*, meaning it wasn't serving already-cached data eagerly. The natural next attempt was `getDocsFromCache`/`getDocFromCache` — a one-time, cache-only read that's supposed to have no network dependency at all — fired in parallel with `onSnapshot` in all three hooks, seeding state from whichever resolved first. Direct timing on that (again a temporary `console.log`) showed it *also* took ~2.2s, landing within ~20ms of Firebase Auth's own `onAuthStateChanged` resolution measured earlier — not a coincidence. The Firestore client SDK funnels every operation, cache-only reads included, through one internal queue that doesn't start processing anything until Firebase Auth's own credential listener has fired at least once (it needs to know whether to attach an ID token, and doesn't distinguish "this particular call is local-only" at the queueing level). So `getDocsFromCache` was never actually independent of network speed here — it was blocked behind the exact same `accounts:lookup` call as `onAuthStateChanged`, just one hop further removed. Our own `effectiveUser` optimism doesn't reach this: Firestore's internal auth-readiness gate listens to the real Firebase Auth SDK directly, not our app's context, so passing an optimistic uid into a query changes nothing about how long Firestore itself waits before running it. Reverted back to plain `onSnapshot`-only in all three hooks rather than carrying the added complexity (a parallel cache read plus a `liveSnapshotReceived` race guard) for zero actual benefit. The one thing that *would* genuinely fix this — mirroring actual budgets/transactions/currency data into `localStorage` ourselves, bypassing Firestore's client entirely for the first paint, the same pattern `effectiveUser` already uses for identity — was identified but not implemented: real added complexity (staleness handling, and transaction history is explicitly unbounded per the Insights section below, so it can't be mirrored wholesale the way the small, bounded user object could) that needs a deliberate decision, not a reflexive addition. **Decided to leave it as-is** — shell and identity render instantly regardless of connection quality now; data lazy-loads behind the same bounded (not indefinite — see the service-worker `accounts:lookup` writeup above) window Firebase Auth itself takes. Accepted as a reasonable landing point rather than taking on the added complexity for further gains.

  **Mirroring `budgets` to `localStorage` (the same way `effectiveUser` mirrors identity) was tried and reverted — don't re-attempt without solving the staleness problem first.** Real-device 3G testing showed the `budgets`-empty-during-load window is worse than "looks slow": since a budget is mandatory for an expense (see Dashboard below), an empty `AddTransactionSheet` picker fully blocks logging one. Seeding `budgets` from a `localStorage` mirror on mount fixed that, but introduced a correctness gap that outweighed it: a budget deleted or edited on another device wouldn't be reflected until the real snapshot arrived, so a transaction added against a stale, since-deleted budget id would get a permanently dangling `budgetId` (existing orphan-cleanup in `deleteBudget` only sweeps transactions that exist *at delete time* — one created later from a stale cache is never caught), and — since the Budgets page's own row list isn't gated on `loading` — editing a since-deleted cached budget would call `updateDoc` on a doc that no longer exists, failing silently (no write-error surfacing anywhere in this app) while the sheet closes as if it saved. Decided the honest "still loading" pill was the better trade than a picker that's fast but occasionally wrong. `useTransactions` and `useBudgets` both still expose `loading` for that pill (`components/loading-pill.tsx` — a small top-anchored pill shown on Dashboard/Budgets/Insights while their respective hooks are loading), and the empty-state copy on all three pages, plus the "add a budget first" copy in `AddTransactionSheet`, is gated on it so a slow connection reads as "loading" rather than "no data here" — but nothing renders optimistically ahead of Firestore actually answering. Both hooks also re-enter `loading` on the browser's `online` event, not just on mount — coming back from a dropped connection is the same "please wait, still syncing" moment as the first load, and without this the pill only ever showed once per page mount.
- `lib/data.ts` — **not** a data source (the old hard-coded expense array was removed once Firestore was wired up). It's shared types (`Transaction` — a discriminated union on `type: "expense" | "income"`, only the expense variant carries an optional `budgetId`; `Budget` — `{ id, name, amount, cadence: "monthly" | "one-time" }`) and formatting helpers (`formatCurrency(value, currency?)`, `relativeDay` — handles both past *and future* dates, needed once `add-transaction-sheet.tsx` let the date be anything, not always today. Only ever says "today"/"yesterday"/"tomorrow" — anything further out in either direction falls straight to the literal date ("4 Sep"), deliberately **not** "N days ago"/"in N days" — that was tried and dropped since a reader has to do the subtraction themselves to know what day that actually was, which defeats the point of a relative label past a one-day offset — `currentMonthLabel`, `todayISO`/`toLocalISODate`). `formatCurrency`'s `currency` param defaults to `DEFAULT_CURRENCY` ("EUR") but every real call site in the app passes the user's actual selection explicitly — see Currency below. **Above €1,000,000 it abbreviates** ("€1.2M", "€1.5B", "€2.5T") instead of printing every digit — a large sum (a total, a running one-time budget, …) could otherwise overflow a fixed-width display like the dashboard's hero "Net" figure; truncating with an ellipsis was ruled out since hiding digits off a money figure is actively misleading. `components/amount-input.tsx` separately caps what a user can actually *type* at 999,999,999.99 (`MAX_AMOUNT`) — but that only bounds a single amount; a *sum* (Net, Budgets' Total, a one-time budget's running total) isn't bounded by it at all, since there's no limit on how many transactions or budgets can exist, so `formatCurrency` has to scale past billions too, not just the one tier a capped single entry could reach. Its `UNITS` ladder (M/B/T) handles the boundary case where rounding would otherwise print "1000M" instead of bumping to the next tier up, at every step, not just M→B. T is the top tier, with nowhere left to bump to — past that (a sum reaching into the quadrillions, unrealistic but not impossible given sums are unbounded), `formatCurrency` prints a plain `"-"` instead of a wrong number like "1000T", signaling "too large to display" rather than showing something misleading. Below €1M, full comma-grouped precision as always.

### Currency (`lib/currencies.ts`, `lib/use-currency.tsx`)

`lib/currencies.ts` is a short list of major currencies — USD, EUR, JPY, GBP (`CurrencyCode`, `currencies`, `currencyMap`, `DEFAULT_CURRENCY` = "EUR") plus a synthetic `"OTHER"` entry — each with a **hardcoded** `symbol` ($, €, ¥, £). Deliberately not delegated to `Intl.NumberFormat`'s own currency-symbol data — ICU doesn't have a clean glyph for every currency (Swiss Franc, for one, just renders as the literal code "CHF" under `style: "currency"`), so this always shows exactly the symbol given here. The list went through a few rounds of curation before landing here — first tried keeping only currencies with a "pure" single-glyph symbol, then tried collapsing symbol-sharing currencies (USD/CAD/AUD all sharing `$`, etc.) down to one generic representative each, then briefly expanded to 8 named currencies with hand-picked distinguishing symbols (A$, C$, Fr., 元) — before settling on this smaller, symbol-only set. USD's label is "Dollar" rather than "US Dollar" (no other dollar-family currency is in the list to disambiguate from); EUR/JPY/GBP keep their normal names. `formatCurrency` (`lib/data.ts`) never uses `Intl`'s `style: "currency"` at all, only `style: "decimal"` for the number, with `currencyMap[currency].symbol` prepended manually (sign handled separately so negatives read `-$12.34`, not `$-12.34`). `"OTHER"`'s symbol is `""`, so this naturally prints a bare number with no prefix for it — no special-casing needed in `formatCurrency` itself, though `components/currency-picker-sheet.tsx` does skip the `(symbol)` suffix for it (every other row is `"{label} ({symbol})"`) since empty parens would look broken. `lib/use-currency.tsx` is a `CurrencyProvider`/`useCurrency()` Context (same reasoning as `AuthProvider`: many components format money, so one shared subscription beats each mounting its own listener on the same doc), scoped to `/users/{uid}/settings/preferences` → `{ currency }`, wrapped around `AppShell` in `app/(app)/layout.tsx` (inside `AuthProvider`, since it needs `useAuth()`'s `user`) — scoped to just the authenticated route group rather than the root layout, since the public marketing page never formats money and doesn't need its own listener on that doc. Every component that calls `formatCurrency` or shows a currency symbol calls `useCurrency()` itself rather than receiving `currency` as a threaded-down prop — that includes `dashboard.tsx`'s local `BudgetCard` — consistent with how `useAuth()` is already called directly wherever needed rather than prop-drilled.

Changed from Settings (`app/(app)/settings/page.tsx`) via `components/currency-picker-sheet.tsx` — a bottom sheet listing all `currencies` (name + symbol in parens, current selection checked — including "Other", which renders as literal empty parens `()` rather than being hidden, showing there's genuinely nothing there instead of omitting the row's usual structure), opened by a small button showing just the current symbol with **no text fallback** — selecting "Other" leaves the button showing nothing but its chevron, which is the point (the word "Other" never appears on the trigger, only inside the sheet). That trigger button and the "Delete account" button in the row below share the same `min-w-20` (a floor, not a fixed width — either can still grow past it if its content ever needs more room) plus identical padding/text-size/centering, so the two rows' right-hand controls line up; the floor still matters since a bare `$` is much narrower than other symbols, and letting the pill shrink-to-fit made it visibly resize as the selection changed. **Deliberately not a native `<select>`** — an earlier version used one, but a native select's open dropdown can't be restyled away from the browser/OS's own default appearance (white background, system font, no dark-theme support), which looked out of place; a native `<select>` also needs `text-base` (16px) to avoid iOS Safari's focus-zoom, which made it visually mismatched in height against its sibling row's `text-xs` "Delete" button. The sheet-based picker sidesteps both problems — full control over styling since it's just app markup, and the trigger is a plain button that can stay `text-xs` like everything else in that row, since a button doesn't trigger the zoom behavior a real form field does. The amount inputs in `add-transaction-sheet.tsx` and `add-budget-sheet.tsx` show `currencyMap[currency].symbol` instead of a hardcoded `€` (see the Budgets section below for how that's positioned).

### Shared UI pieces

- `components/sheet.tsx` — **the app's one modal/bottom-sheet shell.** Every dialog in the app (`add-transaction-sheet.tsx`, `add-budget-sheet.tsx`, `budget-detail-sheet.tsx`, `currency-picker-sheet.tsx`, `confirm-dialog.tsx`, `delete-account-dialog.tsx`) renders through `<Sheet>` rather than hand-rolling its own overlay — it owns the backdrop (click to close), the slide-up rounded container, the drag-handle bar, Escape-to-close, and body-scroll-lock while open; each caller supplies only its header/body/footer as children. This exists because those six used to each hand-roll the same markup independently, and it quietly drifted: only the two add/edit sheets had Escape-to-close and scroll-lock, the other four had neither (though all six already closed on backdrop click, since that part happened to get copy-pasted consistently). Configurable per caller: `maxWidth` (`max-w-md` default, `max-w-sm` for the shorter confirm/picker dialogs), `scrollable` (adds `max-h-[80vh] flex flex-col` for a sheet with a long list body — `budget-detail-sheet.tsx`, `currency-picker-sheet.tsx`), `role` (`"alertdialog"` for confirm/destructive dialogs vs the default `"dialog"`), and `zIndex` (`confirm-dialog.tsx` uses `z-[60]` since it can stack on top of an already-open sheet, e.g. deleting a transaction from within `budget-detail-sheet.tsx`).
- `components/sheet-header.tsx` — the title + close (X) button row every sheet uses right after `<Sheet>`'s opening tag. Extracted once four sheets had it duplicated with a stray inconsistency (two used `mb-5`, two used `mb-4`) — this pins it to one value. Takes a `capitalize` flag for `add-transaction-sheet.tsx`'s heading specifically, which is built as `` `${verb} ${txType}` `` (e.g. "Add expense") and needs the second word capitalized too.
- `components/amount-input.tsx` — the big centered euro-sign-plus-number field shared by `add-transaction-sheet.tsx` and `add-budget-sheet.tsx` (was duplicated identically, comment included, before being pulled out). Reads the current currency itself via `useCurrency()` rather than taking it as a prop. `value`/`onChange` stay a plain digit string with no commas — callers (and `Number.parseFloat` elsewhere) never see formatting — but what's actually shown in the `<input>` is live thousands-grouped (typing "100000" displays "100,000") via an internal `groupThousands()`, with the cursor repositioned by counting digits rather than characters (`countDigits`/`positionAfterDigits`) so inserting/deleting a comma-adjacent digit doesn't jump the cursor to a character index that's shifted by the comma itself. On blur, the value is normalized to exactly 2 decimals (`parsed.toFixed(2)`) if it parses, so "100000" settles into "100,000.00" once the user moves on rather than only while a `.` has actually been typed. While typing, decimal digits are capped at 2 (currency doesn't have a third) and a second "." is deduped rather than left in — `Number.parseFloat` silently truncates at a second "." rather than rejecting it, which wasn't obvious from the UI.
- `components/month-stepper.tsx` — the `ChevronLeft`/`monthLabel`/`ChevronRight` control shared by the one-time-budget month picker (`add-budget-sheet.tsx`) and Insights' 1M month browser (see Insights below). Stateless — takes `month`/`onChange`, the caller owns the state and any wrapping layout.
- `components/transaction-row.tsx` / `components/delete-transaction-dialog.tsx` — the title/date/amount/edit/delete list row and its accompanying `ConfirmDialog` wrapper, shared by `budget-detail-sheet.tsx` and Insights' by-date transaction list (see Insights below). `TransactionRow` handles both transaction types (a `+`/`-` prefix in `--accent`/foreground) even though `budget-detail-sheet.tsx` only ever passes expenses — no special-casing needed since it's the same row shape either way.
- `lib/use-demo-aware-data.ts` — the transactions/budgets live-vs-`?demo=1` switching logic shared by `components/dashboard.tsx` and `app/(app)/insights/page.tsx` (see Insights below for what demo mode actually does). Returns granular `transactionsLoading`/`budgetsLoading` rather than one combined flag, since Dashboard needs them separately (passed to `AddTransactionSheet` as `budgetsLoading`) while Insights just ORs them together itself. `generateDummyData()` is only ever called outside production (`null` otherwise), so it doesn't run pointlessly on every real user's page load.

The input is a **fixed `w-[11ch]`, sized for realistic amounts** ("999,999.99" is 10 characters), **not** `MAX_AMOUNT`'s technical ceiling ("999,999,999.99") — this went through a few wrong turns worth knowing about if it comes up again: sizing the box for the true maximum kept a normal amount like €45.00 looking off-center, since centered text only fills part of a box that wide; resizing the box to fit content on every keystroke (via the native `size` attribute) fixed that but made the whole row visibly jitter left while typing, since re-centering on every character shifts existing digits left while the matching growth on the right (needed to keep it centered) has nothing visible to show for it. A fixed, modest box sidesteps both: **correct centering for every realistic amount**, and a genuinely huge one (approaching `MAX_AMOUNT`) just falls back to the input's own contained horizontal scroll — a deliberate tradeoff, not an oversight, since nobody's actually logging a near-billion-euro personal expense. The symbol and the amount are positioned **independently of each other**, not as one adjacent unit — the symbol is `absolute` at `left-0` of the full-width root, aligning flush with every other label in the sheet ("Description", "Budget", …), while the amount is centered on its own within that same full width via a nested `flex justify-center`, unaffected by the symbol's width or position. (An earlier version anchored the symbol relative to the input itself — `right-full` — so the pair moved together and the symbol ended up wherever the centered input happened to land, not aligned with the rest of the sheet; that positioning was also what an even earlier mobile-overflow bug traced back to, though this version is safe regardless since the box is fixed and modest rather than growing toward the container's own width for large numbers.)

The input itself is a **fixed** `w-[16ch]` (comfortably fits "999,999,999.99", the longest possible value at `MAX_AMOUNT`, 15 characters — with a `min-w-0 max-w-full` backstop, since a flex item's default `min-width: auto` can otherwise refuse to shrink below an explicit width and push the row past the sheet's edge on the narrowest viewports), not resized per keystroke. A version that resized the input to fit its content on every keystroke (via the native `size` attribute) caused the whole row to visibly jitter left while typing — the row re-centers on every character, so existing digits shift left each time while the matching growth on the right has nothing visible to show for it. **Nothing about this layout changes while typing now, only the text content does**, so there's nothing left to jitter. `text-left`, not centered, is what actually closes the gap between the symbol and a short number: centered text in a wide fixed box sits in the box's middle regardless of how much of it the number actually needs, while left-aligned text always lands immediately next to the symbol.

`Sheet` also tracks a module-level `openStack` (ids from `useId()`, pushed/popped as each instance's `open` prop goes true/false) so that when two sheets are stacked, **Escape only closes the topmost one** — the same as clicking outside already does, but for a different reason: a backdrop click only ever reaches the front sheet naturally (its full-screen backdrop physically covers whatever's behind it), while Escape is a single global `keydown` that every currently-open sheet's listener receives regardless of stacking, so without this check the *back* sheet would close first on the first Escape press (a real bug that shipped briefly) rather than the front one.

`Sheet` takes an optional `onConfirm` — Enter calls it, same topmost-stack gating as Escape, skipped only when focus is on a button/link/textarea *inside the dialog itself* (so a focused Cancel button's own Enter-click behavior isn't fought, and a textarea still gets a literal newline). That "inside the dialog" qualifier is load-bearing, not decorative — a real bug, caught immediately after shipping: `Sheet` never moved focus anywhere on open, so whatever triggered the sheet (almost always a button — a trash icon, a "Delete account" row) stayed focused underneath it, and the button-type check alone treated that stale, unrelated focus as a reason to defer to native behavior — meaning Enter silently did nothing in every confirm dialog, Escape being the only key that worked. Fixed by giving the dialog panel itself a `ref`, `tabIndex={-1}`, and focusing it in a `useEffect` on open — but only when nothing inside the dialog is already focused, so `delete-account-dialog.tsx`'s own `autoFocus` input (which wins the race since `autoFocus` is applied during React's commit, before any `useEffect` fires) isn't fought over. Only `confirm-dialog.tsx` and `delete-account-dialog.tsx` pass `onConfirm` — both previously had zero keyboard path to confirm at all. The two add/edit sheets (`add-transaction-sheet.tsx`, `add-budget-sheet.tsx`) don't: they already get Enter-to-submit for free from their own `<form onSubmit>`, and adding `onConfirm` on top would double-fire.
- `components/confirm-dialog.tsx` — the app's only confirm pattern for destructive-but-not-catastrophic actions (deleting a single transaction, deleting a budget). Built once and reused rather than duplicating the modal markup at each call site (each caller owns its own `open`/target state and passes in a title + description); native `confirm()`/`alert()` are avoided everywhere — they look and behave inconsistently on mobile and don't match the app's design. `components/delete-account-dialog.tsx` (Settings) is deliberately **not** built on `ConfirmDialog` — account deletion needed a heavier, type-"delete"-to-confirm flow, different enough from a plain yes/no that reusing it would have meant bolting extra props onto a shared component for one special case. Both still go through `Sheet` for their actual shell, just with different content.
- `components/empty-state.tsx` — the shared "nothing here yet" box (monochrome card, bordered, a colored icon in a circle, instructional text below). Used by `app/(app)/insights/page.tsx` (no transactions yet), `app/(app)/budgets/page.tsx`'s empty list, and `components/dashboard.tsx`'s empty-budgets state.

### Dashboard (`components/dashboard.tsx`)

Built around net worth rather than a spending list: header (a plain "Welcome back!" greeting — an earlier version showed the month/year here instead, and a small avatar circle with the user's initial before that, removed as clutter; the month/year label moved down to sit above the budget cards instead, replacing what used to say "Budgets" there), then one row holding "Net" (this month's income minus expenses, the hero number, `items-end`-aligned against the two smaller figures beside it) with "Spent" and "Earned" to its right — all three in one horizontal row, each with its label stacked above its amount, not the whole trio stacked as separate rows, via `justify-between` with only two flex children — Net flush to the row's start, and a `Spent`+`Earned` sub-group (its own `gap-5`) flush to the end — rather than a fixed `gap` across all three, which spread `Spent` toward the middle instead of keeping it paired with `Earned`. Below that, stacked budget cards (one per budget from `lib/use-budgets.ts`, largest amount first) under a plain month/year label (via `currentMonthLabel()`) — **not a link**; navigation to `/budgets` happens only through the main nav and, when the list is empty, the empty state's inline link (see below), not a second in-page control that would duplicate it. There is deliberately **no transaction list on the dashboard itself** — tapping a budget card opens `components/budget-detail-sheet.tsx`, a bottom sheet listing that budget's matching transactions, each with edit (pencil) and delete (trash) icons. A budget card's progress bar is `--accent` normally; if `spent > amount` it switches to `--danger` and fills to 100% regardless of how far over. The empty-budgets state uses `components/empty-state.tsx`; only the word "Budgets" inside the sentence is a link, styled bold white (`font-bold text-foreground`) with **no underline** — clickability is signaled instead by `hover:scale-110` (the word grows slightly on hover), since underline-on-hover was deliberately dropped in favor of that.

"Spent" is computed differently depending on a budget's `cadence`, via `lib/data.ts`'s `budgetSpending()` (shared with `app/(app)/insights/page.tsx` — see Insights below, which needs the exact same per-budget numbers rather than a second, possibly-diverging calculation) — **monthly** budgets sum this calendar month's matching expenses (resets every month, budget itself always shows); **one-time** budgets are scoped to a single specific month, stored as `Budget.month` ("YYYY-MM", set once at creation and preserved across edits — see Budgets below) — matching expenses are summed only within that one month, and the budget itself is filtered out of `budgetSpending()`'s result entirely once `month` isn't the current month, so it drops off the dashboard on its own the moment that month ends rather than needing to be deleted. **This replaced an earlier design worth knowing about if it resurfaces in old notes**: one-time budgets used to have no month at all and just summed *every* matching expense ever, forever, as a running total that always stayed on the dashboard (a "New laptop" or "Vacation fund" savings-goal style target) — dropped because it didn't fit the actual use case driving this cadence: a single trip (e.g. "Vienna"), contained to the month it happens in, with no reason to keep cluttering the dashboard once the trip's over. The same month-scoping carries into `budget-detail-sheet.tsx`'s transaction list, since `budgetSpending()` returns each budget's already-scoped `transactions` alongside its `spent` total — its empty state always reads "No transactions this month" now (not conditional on cadence), since both cadences are month-scoped at this point, just one recurs and one doesn't.

Opening the add form is responsive: mobile keeps the floating FAB (fixed bottom-right, `md:hidden` — thumb-reachable, the standard mobile convention), while desktop hides that and shows an inline circular button next to the month label instead (`hidden ... md:flex`, `size-11`, solid `bg-accent`, just a `Plus` icon, no text) — a fixed corner-anchored circle read as disconnected from the rest of the page on a wide desktop viewport, so desktop moves it inline near the header, in the same spot Budgets' "Add budget" button occupies on its own page. Deliberately **not** styled as a pill-with-text like that button, though — this is the app's primary action, the same weight as the FAB itself, so it keeps the FAB's own circle-with-plus shape rather than reading as a sibling of a page-scoped secondary action. Both trigger the same `components/add-transaction-sheet.tsx`, which has an Expense/Income toggle at the top — **only when adding**; when editing (`editing` prop set) the toggle is gone with nothing in its place (an earlier version showed a static "Expense"/"Income" label there instead, but that read as redundant clutter — the amount and description are enough context), since a transaction's type can't be changed after creation (switching an expense to income would need to somehow reattach or strand its `budgetId`, which is confusing either way — simplest to just not allow it). For Expense, budget pills are generated dynamically from the user's actual budgets (`budgets` prop, passed down from `components/dashboard.tsx`'s `useBudgets`) — tapping one sets `budgetId`. **A budget is required for an expense** (the submit button stays disabled without one — an unbudgeted expense doesn't show up on any budget card, which read as data quietly going missing rather than a valid state).

**Zero budgets blocks the whole form, not just the budget picker** — `blockedOnNoBudgets` (`!editing && txType === "expense" && !budgetsLoading && pickableBudgets.length === 0`) swaps the entire amount/date/description/budget-picker form for a single centered message + an "Add a budget" link (`href="/budgets?add=1"`, closes this sheet via `onClose` and jumps straight to Budgets, which reads `?add=1` on mount to auto-open its own `AddBudgetSheet` and strips the param via `router.replace("/budgets")` so a refresh doesn't reopen it). **This replaced an earlier version worth remembering if it comes up again**: a small circular `+` sat inline with the budget pills, shown even when budgets already existed, as a shortcut to add another one mid-transaction. Real bug, reported directly: someone filling in amount/description first and only then noticing "add a budget" would navigate away and lose everything they'd already typed, since the pills sit at the *bottom* of the form. Blocking the whole form the moment the sheet opens (when it's a new expense with nothing pickable) means there's nothing to lose — the amount field never even renders. The Expense/Income toggle stays outside this block and always renders, so switching to Income (which needs no budget) is never blocked. Editing is deliberately exempt (`!editing`) — an existing expense's fields should stay visible regardless of budget state. **Description is optional** — only amount (and budget, for an expense) are required; if left blank, the stored `title` falls back to `"-"` rather than an empty string, so nothing renders as a blank row wherever `title` is displayed later. The same sheet component handles both adding and editing: an `editing: Transaction | null` prop pre-fills the form and switches `onAdd` to `onUpdate` on submit; `components/dashboard.tsx` opens it in edit mode from the budget detail sheet's pencil icon.

The **Date** field is a small standalone gold pill (`border-accent/40 text-accent`, no separate label — the pill itself, showing `relativeDay(date)` — "today"/"yesterday"/"tomorrow", or a short date beyond that — is self-explanatory) that opens `components/date-picker-sheet.tsx`, a from-scratch calendar grid (Monday-first week, matching the `en-IE` locale used elsewhere) rather than a native `<input type="date">` — same reasoning as the currency picker: a native date input's popup can't be restyled to match the dark theme. Defaults to today (`lib/data.ts`'s `todayISO()`) for a new transaction, or the transaction's existing date when editing. `todayISO()`/`toLocalISODate()` build the ISO string from local year/month/day rather than `Date#toISOString()` (UTC-based, which silently shifts the date near midnight in timezones ahead of or behind UTC) — `lib/use-transactions.ts`'s `addTransaction` used to auto-stamp `new Date().toISOString().slice(0, 10)` itself, which had exactly that latent bug; the date is now just a normal field on `NewTransaction` that the sheet supplies, defaulting via the correct local-date helper.

`components/budget-detail-sheet.tsx` also shows the same spent/limit text + progress bar treatment as the dashboard's budget cards, right below the title — it sums the `transactions` prop it's given (already scoped to the right window by the caller) rather than taking a separate `spent` prop, since that sum is the same number the card already computed.

### Budgets (`app/(app)/budgets/page.tsx`)

Where budgets are actually created/edited/deleted (the dashboard only reads and displays them). Below the title/add-button header row, a "Total" stat (sum of every budget's `amount`, regardless of cadence) uses the exact same label-then-hero-number treatment as the dashboard's "Net" (`text-xs text-detail` label, `mb-0.5`, then `text-[34px]` for the amount) for visual consistency between the two. A quiet, outline-style "Add budget" button (`border-accent/40 text-accent`, not a solid fill — deliberately less loud than the dashboard's solid-accent FAB) opens `components/add-budget-sheet.tsx`, which asks for amount, name, and cadence ("Monthly budget" / "One-time budget"). The cadence control is a small binary switch (`role="switch"`, a 36×20px pill track with a sliding thumb — the thumb needs an explicit `left-0.5` anchor plus a `translate-x` for the slide, **not** just a bare `translate-x` with no `left` set, which left it relying on the browser's implicit static-position fallback and made it render outside the track), not a wide segmented-pill toggle like Expense/Income in the transaction sheet — deliberately kept quiet/low-emphasis since it's a secondary setting, not the primary decision on the form the way expense-vs-income is. Laid out like the other fields — a `text-xs text-detail` "Repeats" label above, same as "Name" — with its current-value text ("Every month" / "One month only") sitting directly beside the switch itself (not spread apart via `justify-between` across the full row, which read as two disconnected pieces rather than one control), plus a one-line caption below spelling out what each state actually does ("Resets to zero at the start of each month" / "For a trip or other one-off spending — only counts expenses in the month below, then disappears from the dashboard") — the switch alone didn't explain what "monthly" vs "one-time" meant in practice, and specifically didn't convey that it's scoped to a single month at all (real user confusion this wording is meant to head off). Doubles as the edit form via an `editing: Budget | null` prop, same pattern as `add-transaction-sheet.tsx`. Both this sheet's and `add-transaction-sheet.tsx`'s big amount input show the currency symbol (`currencyMap[currency].symbol` — was a hardcoded `€` before multi-currency support) via `components/amount-input.tsx` — see that entry above for how the symbol stays centered against the number without risking rendering outside the sheet on mobile. The budgets list itself is sorted largest-to-smallest by amount; each row is a plain `py-3` list item divided by `border-b border-border` — **deliberately no card border/rounding** here (a version that borrowed the dashboard budget cards' bordered shell, to force matching height/width between the two screens, was tried and reverted; the two are allowed to look different, this list doesn't need to visually match the dashboard's cards). Each row has the name, cadence, amount, and edit/delete icons (delete goes through `components/confirm-dialog.tsx`), plus a thin fixed-accent-color line underneath every row — **not** proportional to amount, purely decorative, identical on every row regardless of size (an earlier version varied its width by amount, which read as a meter and was confusing since nothing about it was actually fillable — dropped for exactly that reason). Empty state uses `components/empty-state.tsx` with the `Wallet` icon (same icon as the Budgets nav item).

A budget name must be unique (case-insensitive, trimmed) and capped at 30 characters (`MAX_NAME_LENGTH` in `add-budget-sheet.tsx`, enforced both as an input `maxLength` and in the submit-disabling `valid` check, alongside the amount/name-presence checks already there) — this is `add-budget-sheet.tsx`'s own concern rather than something `lib/use-budgets.ts` enforces on write, same division of labor as the amount cap in `components/amount-input.tsx`.

A one-time budget's target month (`Budget.month`, "YYYY-MM") is an explicit choice, not an implicit stamp: a small month stepper (`ChevronLeft`/`ChevronRight` either side of `monthLabel(month)`, `lib/data.ts`'s `shiftMonthKey()`) appears under the switch whenever cadence is "one-time," defaulting to the current month but movable to any past or future month. **This replaced an earlier, more confusing version** where the month was silently set once at creation to "whichever month it's first created in" with no UI for it at all — meaning a "Vienna" budget created in September for an October trip would scope itself to September and vanish from the dashboard before the trip even started. The picker fixes that: plan a trip budget ahead of time, land on the right month. Editing an existing one-time budget initializes the stepper to its already-saved month rather than jumping to "now." Switching a budget's cadence from one-time back to monthly has to explicitly clear the stale `month` field via `deleteField()` in `lib/use-budgets.ts`'s `updateBudget` — same reasoning, and same fix, as `use-transactions.ts` stripping `budgetId` when a transaction's type flips to income. The Budgets list (this page) shows a one-time budget's actual target month (`monthLabel()`, e.g. "Jun 2026") in place of the plain "One-time" cadence label the dashboard would use, since multiple past trips read as indistinguishable without it — falls back to the literal string "One-time" only for a pre-existing budget saved before `month` existed. `add-transaction-sheet.tsx`'s budget picker similarly filters out one-time budgets whose month isn't the current one (a finished trip — or one that hasn't started yet — shouldn't be offered when logging a new expense) — except the transaction's own already-assigned budget stays selectable regardless, so editing an old expense never finds its budget missing from the list.

**A dev-only fake-"today" override (a floating pill, prev/next-month steppers, backed by a `now()` indirection in `lib/data.ts` reading `localStorage`) was tried and removed.** It let a one-time budget's disappearance be watched happening on the real Dashboard without waiting for a real month to change, but it also introduced a real hydration-mismatch risk (the server never sees the override; the client's first render does) that needed its own fix on top. Removed once Insights' 1M month-browser (below) made it redundant for the case that actually mattered day to day — every date function (`todayISO()`, `currentMonthLabel()`, `isThisMonth()`, `relativeDay()`) is back to calling `new Date()` directly, no indirection. Note this doesn't cover *every* thing the override did: Insights' month-browser only changes what that page displays for a chosen month, it doesn't change what "today" means for the rest of the app, so the Dashboard's own cadence-based expiry (`budgetSpending()`) still can't be watched happening without either waiting for a real month or re-adding some form of this.

**Every new account is seeded with 5 default budgets** (Groceries, Housing, Transportation, Coffee, Eating out — all `monthly`, with round placeholder amounts) instead of starting from an empty list — feedback was that a brand-new account with zero budgets read as broken/overwhelming rather than blank-by-design. Seeded from `lib/use-auth.tsx`'s `signInWithGoogleCredential`, gated on the Firebase user's own `metadata.creationTime === metadata.lastSignInTime` (only equal on a genuine first-ever sign-in) so an existing user who deletes all their budgets deliberately doesn't get them silently repopulated on their next login. `DEFAULT_BUDGETS`/`seedDefaultBudgets()` live in `lib/use-budgets.ts` rather than `use-auth.tsx` itself, consistent with that file owning all reads/writes to the `budgets` collection.

### Insights (`app/(app)/insights/page.tsx`)

Two sections, both reading from the same `useTransactions`/`useBudgets` data the rest of the app already uses (deliberately no data-retention/history-trimming work yet — see below), and both driven by the same period pills (1M / Q1 / Q2 / Q3 / Q4 / Full year / All time — the pill row is `flex-wrap` since seven pills runs wider than the sheet on narrow screens) at the top of the page — per the usual dataviz rule that a filter scopes *everything* below it, so the chart and the ranked list always agree on what window they're describing. **1M is the default** (`useState<Period>("month")`) rather than Full year — the page opens straight into the month-browsing view described below instead of a multi-month aggregate.

**Quarters are calendar-aligned, not rolling windows, and deliberately scoped to the current year only** — Q1–Q4 replaced an earlier "Quarter"/"Half year"/"Full year" trio that meant "the trailing 3/6/12 months from today," on explicit feedback that a rolling window is genuinely hard to reason about (if today's mid-September, what months is "6 months back" even covering?). A calendar quarter needs no arithmetic — everyone already knows what Q3 means. `periodToRange()` (local to this page, not `lib/data.ts` — the data layer doesn't need to know what a "quarter" is, only a start/end month) maps each pill to a `MonthRange` (`lib/data.ts`'s `{ startMonth, endMonth } | null`, `null` meaning all time); Q1–Q4 and Full year all resolve against `new Date().getFullYear()`, so **a past year's Q3 currently has no dedicated view** — falling back to "All time" and reading the chart is the only way to see it for now. That gap is deliberate and known, not an oversight: a per-year scroller (mirroring 1M's month browser) was considered and explicitly deferred, pending a separate decision about compressing past years into something more compact once there's enough history to matter, rather than letting every past year accumulate its own full set of quarter pills.

1. **Chart** (`components/insights-chart.tsx`) — monthly spend vs. income, as two line series over the selected period (filtered client-side from `lib/data.ts`'s `monthlyTotals()`). Spend is the primary series (gold `--accent`, with a faded gradient area fill under it — an SVG `<linearGradient>` from ~22%-opacity gold at the line down to fully transparent at the baseline, via `useId()` for a collision-safe per-instance gradient id; a flat low-opacity fill was tried first and read as "plain," not faded); income is a plain 2px line at 70% opacity in the app's own `--foreground` white/off-white — deliberately *not* a second brand hue: this is a primary-vs-context pairing (spend is the story, income is there for scale), not two equally-weighted categorical identities, so it borrows the existing text-foreground token rather than adding a new brand color. Deliberately two *lines* on one shared axis, not a dual-axis chart, since spend and income are both currency amounts (a second y-axis is the #1 chart-design mistake for exactly this "two measures, same unit" case). The chart's `<svg>` uses `w-full` for a responsive width, and its CSS `aspect-ratio` is set to match the viewBox's own aspect ratio (`${WIDTH} / ${HEIGHT}`) rather than a fixed pixel height — an earlier version paired `w-full` with a fixed `height: 150px`, which almost never matches the viewBox's aspect ratio (300:116) exactly, so the browser's default `preserveAspectRatio="xMidYMid meet"` scaled the whole viewBox down to fit *inside* that mismatched box and letterboxed it — centered, with invisible empty margins on both sides that had nothing to do with any internal padding. `aspect-ratio` fixes that generally, without the distortion a blunter `preserveAspectRatio="none"` fix would have caused (that stretches non-uniformly, visibly squashing the circular end-markers into ellipses whenever the container's width doesn't happen to match). `PAD_LEFT`/`PAD_RIGHT` (14 units each) exist purely so the x-axis month labels — 3-letter, `textAnchor="middle"`, sitting exactly at the first/last plotted x position — have enough room not to clip past the SVG's own edges; the value is sized for that specific text, not chosen for visual spacing.

**No numeric y-axis at all** — the 3 gridlines (0 / half / a "nice" rounded max via `niceCeiling()`) are purely visual guides with no value labels next to them; an earlier version showed the rounded values, removed on request. They're dotted (`strokeDasharray="2,3"`), not solid — a deliberate style call overriding the dataviz skill's usual "gridlines are solid hairlines" default, since this is a specific aesthetic choice for this chart rather than an oversight. The x-axis still gets month labels, thinned to roughly 6 when there'd otherwise be too many to fit (`labelStep = Math.ceil(points.length / 6)`, always keeping the most recent month's label even if it'd otherwise be skipped by the stride). **No hover/crosshair interaction** — an earlier version tracked pointer position with a crosshair line and a tooltip card; both were removed (the tooltip first, once the page already had a Spent/Earned figure making it redundant; the whole hover mechanism shortly after, on request, to keep the chart non-interactive for now). What's left is a static end-of-line marker (one dot per series) fixed at the most recent point, not tied to any pointer state.
2. **Budgets, ranked** — no section label (an earlier "Budgets, ranked" heading was removed as unnecessary — the ranked list is visually self-explanatory right under the chart). Every budget with at least one matching expense **inside the selected period**, sorted by that period's spend, highest first, via `lib/data.ts`'s `budgetSpendingInPeriod(budgets, transactions, period)` — deliberately *not* the cadence-aware `budgetSpending()` the Dashboard uses (which is always "this calendar month" for monthly budgets, "ever" for one-time ones, with no period concept at all). Insights instead scopes strictly to the period's actual date range regardless of a budget's own cadence, and **drops any budget with zero matching transactions in that window** — a one-time budget funded 4 months ago won't appear under 1M or 3M, only once the selected period reaches back far enough to include that transaction. This was a deliberate correction: an earlier version reused the Dashboard's cadence-based figure directly, which meant a one-time budget's all-time total kept showing up under every period pill including 1M even with zero activity that month — confusing next to a chart and hero numbers that *do* change with the period. Tapping a row still reuses `budget-detail-sheet.tsx` unchanged, passed that row's period-scoped `transactions`.

Each row also gets a thin gold line underneath (`h-[3px] bg-accent`, same visual language as `app/(app)/budgets/page.tsx`'s per-row line) — but unlike that one, which is explicitly fixed-width and decorative (see Budgets above), this one's width is proportional to `spent / maxSpent` across the currently ranked set, turning it into a simple comparative meter so the largest-to-smallest gap between budgets reads at a glance. The two pages showing the same visual element with different meaning is intentional, not an inconsistency — Budgets' list is a management view (nothing there is "fillable"), Insights' list is specifically about relative comparison.

`lib/data.ts`'s `budgetSpending()` (Dashboard's cadence-aware, period-less version) and `budgetSpendingInPeriod()` (Insights' period-scoped version) share a private `periodStartMonth()` helper with `monthlyTotals()` for computing a period's start month, but are otherwise separate functions with different semantics — don't try to unify them further; the period-vs-cadence distinction is the point, not an accident of two similar-looking functions.

**The 1M pill is a month browser, not just "the last bucket"** — the only period with a `MonthStepper` (`browsedMonth` state, `lib/data.ts`'s `shiftMonthKey()`) letting you step to any month, not just the real current one. The stepper sits in the "Spending history" row *below* the chart, not above it — an earlier version put it above, between the period pills and the Spent/Earned figures, which meant the chart's own position shifted up and down every time you switched between 1M and any other period pill. Below the chart, nothing shifts what's above it, so the chart stays put regardless of which pill is active. The whole "Spending history" header row (stepper on the left, budget/date view toggle on the right) is styled as one pill (`rounded-full border border-border-strong bg-card px-2 py-1`) — the row read as bare/squished without a container — which doubles as a visual divider between the chart and the list below it, not just a control bar. This is what finally gives the app a way to fix an old expense: `lib/data.ts`'s `monthlyTotals()` and `budgetSpendingInPeriod()` both take a `MonthRange` — `{ startMonth, endMonth }` (both "YYYY-MM") or `null` for all time — instead of the "N trailing months" + optional reference-month pair they used to. `null` resolves (via the private `resolveRange()`) to the earliest transaction's month through the current month, same as before. `endOfMonthISO()` (exported) is the actual upper-bound ISO date for a range's `endMonth` — the real end of that calendar month, not "today," which only makes sense when the range happens to include the current month. `MonthRange` deliberately lives in `lib/data.ts`, not the page — it's a generic "here's a date window" concept, agnostic to whether the caller built it from a month, a quarter, or a year.

Below the chart, 1M **only** additionally shows a "Spending history" section whose header row is the `MonthStepper` on the left (see above) and a small two-icon view toggle on the right (`historyView: "budget" | "date"`, styled like a Windows-Explorer view switcher — deliberately not a bigger segmented control, since it's a secondary, page-scoped choice) — **not shown for Q1–Q4/Full year/All time**, which keep exactly the plain ranked list described above, no toggle, no browsing (a multi-month "list every transaction by date" would run straight into the unbounded-history concern below, and month-browsing a multi-month period doesn't make sense the way it does for a single one). `"budget"` (default) is the same ranked-budgets list. `"date"` is new: a flat, chronological list of *every* transaction in the browsed month — expense **and income together** (`monthTransactions`, filtered straight off `transactions` by date range, not through `budgetSpendingInPeriod`, since that function is expense-only) — each row rendered via the shared `components/transaction-row.tsx` / `components/delete-transaction-dialog.tsx` (see Shared UI pieces above), wired to the same `editingTransaction`/`AddTransactionSheet` this page already renders. Income rows are prefixed `+` in `--accent`; expense rows `-` in the normal foreground color — no color is reused from the danger/over-budget semantics elsewhere in the app. **This is also, incidentally, the first place in the whole app an income transaction can be edited or deleted at all** — a real gap until now (an earlier draft of this page once added a full "all transactions" list specifically to close it; removed at the time per feedback that Insights shouldn't duplicate that surface — this revamp is a deliberate reversal of that call, scoped to 1M only rather than reopening it everywhere). **Income "buckets"/categorization is still an open, undecided question** — nothing here adds a source/category to income, on purpose; this only fixes the edit/delete gap.

**Demo mode for local testing** (`lib/dummy-data.ts`, switching logic shared via `lib/use-demo-aware-data.ts` — see Shared UI pieces above): visiting `/insights?demo=1` **or `/dashboard?demo=1`** in `next dev` (gated on `process.env.NODE_ENV !== "production"`, so this is a no-op in any production build regardless of the query string) swaps that page's `transactions`/`budgets` for `generateDummyData()`'s output — a seeded-random ~1 year of realistic income/expense activity across 4 monthly budgets and 3 one-time trip budgets (Vienna 8 months ago, Rome 3 months ago, Berlin this month — each with a handful of expenses confined to just its own month, `month` set accordingly), generated relative to the real current date (not hardcoded ISO strings) so "this month" cadence logic exercises correctly no matter when it's run. The three trips deliberately span "long over" (Vienna), "recently over" (Rome), and "still in progress" (Berlin) so demo mode exercises both halves of the one-time behavior at once: Vienna/Rome are old news and don't show on the dashboard at all, only Berlin does, while all three still show up in Insights once the selected period reaches back far enough to include them. The current calendar month is deliberately forced net-negative (an extra "Car repair" expense sized to whatever it takes to push that month's spend past its income, computed from the month's own accumulated totals rather than a guessed constant, since the ordinary random expenses alone weren't reliably enough to push it negative on their own) — this exists specifically to exercise the negative-net UI path (Dashboard's "Net" figure going negative, formatted with a leading `-`) without waiting for a real account to actually go over budget. Edit/delete (and add, on the Dashboard) become no-ops in demo mode rather than attempting real Firestore writes against fake document ids. Still requires signing in normally first — demo mode only swaps the *data* a page renders, not the auth gate. **Originally Insights-only**; added to the Dashboard too since it's the one page that implements cadence-based expiry (`budgetSpending()`) — Insights' own ranked list uses the period-scoped `budgetSpendingInPeriod()` instead, which doesn't exercise that behavior at all, so only the Dashboard's demo mode actually shows Vienna/Rome staying gone while Berlin shows.

**Explicitly deferred**: nothing here bounds how much history loads — `useTransactions`' `onSnapshot` still fetches a user's entire transaction collection, same as before this page existed. That's a real scaling concern (Firestore's free-tier read quota is project-wide, not per-user, and an unbounded per-user history multiplies fast), but the plan is to build Insights first, then simulate several years of data for a realistic user count and measure whether some form of history compaction is actually feasible before investing in it — possibly landing as a paid-tier gate instead if it isn't. Don't add consolidation/archiving logic speculatively; it's an open, explicitly-postponed decision, not a missing feature.

### Styling

Tailwind v4 theme tokens are defined in `app/globals.css` via CSS variables + `@theme inline`: `background`, `foreground`, `accent`, `danger`, `detail`, `muted`, `border`, `border-strong`, `card`, `surface`, `radius-card`. Use these token names (`bg-card`, `text-detail`, etc.) rather than raw hex values or ad hoc colors — the one exception is `components/insights-chart.tsx`'s actual SVG `stroke`/`fill` attributes, which use plain hex constants (matching `--accent`'s and `--foreground`'s real values) instead of `var(--accent)`, since CSS custom property resolution inside SVG presentation attributes isn't worth the cross-browser risk for a color that already lives as a real Tailwind token for every other (HTML) use.

Any `<input>`/`<textarea>`/`<select>` needs `text-base` (16px) or larger — iOS Safari auto-zooms the page on focus if a form field's font size is under 16px. There's no global guard against this (a blanket CSS rule would also shrink the intentionally-large amount input in `add-transaction-sheet.tsx`), so it has to be applied per-field.

### Path alias

`@/*` maps to the repo root (see `tsconfig.json`), e.g. `@/lib/data`, `@/components/dashboard`.

### Environment

Firebase web config lives in `.env.local` as `NEXT_PUBLIC_FIREBASE_*` variables (gitignored, required for `lib/firebase.ts` to initialize). `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is the OAuth Web client ID Firebase auto-created for the Google sign-in provider (same value visible in Firebase console → Authentication → Sign-in method → Google, or Google Cloud Console → Credentials) — required by `AppShell`'s Google Identity Services setup.

**Setup gotcha:** GIS separately requires every origin it'll run from (`http://localhost:3000`, the deployed Vercel domain, etc.) to be listed under that same OAuth Client ID's **"Authorized JavaScript origins"** in Google Cloud Console (APIs & Services → Credentials — a direct link like `https://console.cloud.google.com/apis/credentials?project=<firebase-project-id>` gets there fastest). This is a *different* setting from Firebase's own "Authorized domains" list (Authentication → Settings) — missing it produces a real Google-hosted "Access blocked: Authorisation error" page, not a console warning, so it's easy to mistake for something more exotic if you don't know to look here first.
