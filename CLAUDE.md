# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the dev server
- `npm run build` — production build
- `npm run start` — run a production build

There is no linter or test suite configured in this repo — ESLint was deliberately removed (TypeScript's own diagnostics already cover unused-variable checks; the rest of the overlap wasn't worth keeping for this project).

## Architecture

Fehu is a personal finance tracker PWA: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4, Firebase (Firestore + Auth).

### Routing

Flat structure under `app/` (no route groups). `app/page.tsx` renders the `Dashboard` at `/`, `app/budgets` is a real screen (see Budgets below), and `app/settings` has a real (if minimal) screen — see Auth model below. `app/insights` is still a one-line page rendering `components/page-placeholder.tsx` (icon + description empty state) — no real functionality yet. There is no Categories page or nav item — see Data layer below for why. `app/layout.tsx` wraps every page in `AuthProvider` (from `lib/use-auth.tsx`) and then `AppShell` (from `components/app-shell.tsx`, sidebar on desktop / burger-drawer on mobile, both anchored **left** — the mobile burger button lives at the top-left of the header to match, and the drawer slides in from the left), with nav items sourced from `lib/nav.ts`.

### Auth model (`lib/use-auth.tsx`)

Auth state is a React Context (`AuthProvider`/`useAuth`), not a plain hook — this is deliberate: more than one component (the app shell, the dashboard) needs the same live auth state, and independent `onAuthStateChanged` listeners per hook call risk racing into separate sessions.

**⚠️ This auth system has been through a lot of iteration and is still a little rough around the edges.** Sign-in specifically went through several full redesigns (`signInWithPopup` → `signInWithRedirect` → back to popup with hand-built hang-detection → the current Google Identity Services approach below) chasing a mobile popup-hang bug — see git history / prior session notes for the full saga if something here seems inconsistent or overbuilt. The current approach is confirmed working on desktop (both `localhost` and the deployed domain); **not yet re-confirmed on mobile since the GIS switch** — that's the main thing still worth testing before trusting this area is fully settled.

Sign-in is mandatory and Google-only, currently implemented with **Google Identity Services (GIS)** — Google's own client-side library (loaded via `next/script` in `AppShell`) — rather than Firebase's own `signInWithPopup`/`signInWithRedirect`. GIS renders and manages its own button and popup lifecycle via `renderButton()`; our callback (passed to `google.accounts.id.initialize`) only ever fires with a real credential on success, so there's no "did the user close it" ambiguity to detect at all. The credential is exchanged for a Firebase session via `signInWithGoogleCredential` (`lib/use-auth.tsx`), which wraps `GoogleAuthProvider.credential(idToken)` + `signInWithCredential`.

**Deliberately not using GIS's One Tap `prompt()` flow** (tried it — a custom-styled button calling `prompt()`, with real cancel detection via `notification.getSkippedReason()`). It works, but depends on FedCM, which Chrome can silently suppress for a site after a user dismisses the prompt a few times — with no reliable way to detect or recover from that (Google's FedCM migration guide confirms the detail needed to distinguish this from an ordinary cancel, `getNotDisplayedReason()`, is being removed entirely for privacy reasons). `renderButton()`'s classic popup flow doesn't go through FedCM at all, so it isn't subject to this failure mode — chosen for that reason over the cosmetic benefit of a theme-matched custom button.

Prior to GIS: `signInWithPopup` worked but mobile browsers generally don't support true popup windows, breaking Firebase's own "is the popup still open" detection and leaving the sign-in UI hanging indefinitely if closed without completing. `signInWithRedirect` was tried as a fix but turned out broken more broadly — `getRedirectResult` silently resolving with nothing, reproduced on `localhost` *and* the real deployed domain, desktop *and* mobile, even in a clean Incognito profile (never fully root-caused, suspected browser third-party-storage policy) — and had an unwanted plain full-page-navigation feel besides. GIS was adopted specifically because it sidesteps this entire class of problem by design rather than needing another workaround.

`AuthProvider` exposes a `loading` flag (true until the first `onAuthStateChanged` callback fires) so `AppShell` can avoid flashing the sign-in screen while Firebase checks for an existing session; `AppShell` renders a full-screen sign-in gate whenever there's no `user`, and only renders the app (sidebar/nav/`children`) once signed in. There is deliberately no local-only/anonymous mode — every expense is tied to a real account from the first write, which avoids an earlier class of bugs around orphaned anonymous data and popup/credential-linking edge cases.

`AuthProvider` also exposes `deleteAccount`: deletes all of the user's Firestore docs first — both `transactions` and `budgets` (batched, while still authenticated — Firestore's rules require `request.auth.uid == userId`), then calls `deleteUser` on the Firebase Auth account. There's no top bar or account banner anymore — "Delete account" lives in `app/settings/page.tsx`, gated behind `components/delete-account-dialog.tsx`, a custom modal that requires typing the word "delete" before the delete button enables (replaced an earlier native-`confirm()` version — deliberately heavier-handed than a single confirm click since this is irreversible). "Log out" lives at the bottom of the nav stack in `AppShell` (both the desktop sidebar and the mobile drawer), separated from the regular nav items by a border, rather than in a top bar. Note account deletion doesn't revoke Google's own OAuth consent grant for the app (that's tracked independently by Google, not Firebase) — signing in again with the same Google account afterward won't re-show the permissions screen, since Google still remembers the prior authorization.

Firestore security rules (managed in the Firebase console, not checked into this repo) restrict each user's data to `request.auth.uid == userId`, currently scoped to `/users/{userId}/expenses/**` — **this needs updating manually in the Firebase console** to `/users/{userId}/transactions/**` plus new rules for `/users/{userId}/budgets/**` and `/users/{userId}/settings/**` (the latter added for `lib/use-currency.tsx`), none of which is tracked in this repo. The collection was renamed from `expenses` to `transactions` once income tracking was added, done as a clean rename with no migration path — safe only because there's no real user data yet (pre-launch); this would need an actual migration once the app has real users.

### Data layer

There is **no fixed category list anymore** (no `CategoryId`, no Categories page/nav item) — budgets themselves are the categorization. Each budget is a user-defined `{ name, amount, cadence }`; an expense optionally references one by `budgetId`. This replaced an earlier design (still worth knowing about if it resurfaces in old notes/git history) where categories were a hard-coded 8-item enum (Food, Transit, Bills, …) and budgets were per-category spending caps keyed by that enum — deliberately dropped in favor of the current, fully user-defined model.

- `lib/firebase.ts` — initializes the Firebase app, `auth`, and `db`. Firestore uses `persistentLocalCache` for offline read/write support (writes queue locally and sync when back online).
- `app/manifest.ts` — the web app manifest (`name`, `icons`, `display: standalone`, theme colors matching the app's dark background). Icons live in `public/icons/` at six sizes (48–512px); each file's actual pixel dimensions were verified to match its filename/declaration. `app/layout.tsx`'s `metadata.icons.apple` separately points at the 192×192 icon for iOS's home-screen icon — iOS Safari doesn't reliably read the manifest's icons the way Chrome/Android does, so without this it falls back to an inconsistent or blurry screenshot-based icon.
- `public/service-worker.js` — service worker covering *app-shell* offline support (separate from Firestore's data-level offline support above): network-first for same-origin GET requests, falling back to the cache when offline; deliberately ignores cross-origin requests (so it never intercepts Firestore/Google API calls) and non-GET requests. Registered from `components/app-shell.tsx`, production builds only (`npm run dev` never registers it, so cached code doesn't go stale while iterating). `AppShell` also tracks `navigator.onLine` to show a "no internet connection" message on the sign-in screen instead of a sign-in button that's guaranteed to fail offline.
- `lib/use-transactions.ts` — realtime Firestore hook (`onSnapshot`) scoped to `/users/{uid}/transactions`, ordered by date, exposing `transactions` plus `addTransaction`/`updateTransaction`/`deleteTransaction`. `updateTransaction` also strips the `budgetId` field via `deleteField()` when editing a transaction's type to `"income"`, since income transactions never reference a budget and it would otherwise linger as stale data on the doc.
- `lib/use-budgets.ts` — realtime, full-CRUD Firestore hook scoped to `/users/{uid}/budgets` (one doc per budget, auto-generated id — not keyed by anything fixed), exposing `budgets` plus `addBudget`/`updateBudget`/`deleteBudget`. `deleteBudget` queries `/users/{uid}/transactions` for any doc referencing the budget's id and strips their `budgetId` via `deleteField()` in the same batch as the budget's own deletion — otherwise those transactions would be left with a `budgetId` pointing at a doc that no longer exists (a real bug that shipped briefly: the transactions stayed queryable and correct as standalone expenses, but the dangling reference itself was never cleaned up). They still end up as valid, standalone expense records, just no longer linked to any budget.
- `lib/data.ts` — **not** a data source (the old hard-coded expense array was removed once Firestore was wired up). It's shared types (`Transaction` — a discriminated union on `type: "expense" | "income"`, only the expense variant carries an optional `budgetId`; `Budget` — `{ id, name, amount, cadence: "monthly" | "one-time" }`) and formatting helpers (`formatCurrency(value, currency?)`, `relativeDay`, `currentMonthLabel`). `formatCurrency`'s `currency` param defaults to `DEFAULT_CURRENCY` ("EUR") but every real call site in the app passes the user's actual selection explicitly — see Currency below.

### Currency (`lib/currencies.ts`, `lib/use-currency.tsx`)

`lib/currencies.ts` is a short list of major currencies — USD, EUR, JPY, GBP (`CurrencyCode`, `currencies`, `currencyMap`, `DEFAULT_CURRENCY` = "EUR") plus a synthetic `"OTHER"` entry — each with a **hardcoded** `symbol` ($, €, ¥, £). Deliberately not delegated to `Intl.NumberFormat`'s own currency-symbol data — ICU doesn't have a clean glyph for every currency (Swiss Franc, for one, just renders as the literal code "CHF" under `style: "currency"`), so this always shows exactly the symbol given here. The list went through a few rounds of curation before landing here — first tried keeping only currencies with a "pure" single-glyph symbol, then tried collapsing symbol-sharing currencies (USD/CAD/AUD all sharing `$`, etc.) down to one generic representative each, then briefly expanded to 8 named currencies with hand-picked distinguishing symbols (A$, C$, Fr., 元) — before settling on this smaller, symbol-only set. USD's label is "Dollar" rather than "US Dollar" (no other dollar-family currency is in the list to disambiguate from); EUR/JPY/GBP keep their normal names. `formatCurrency` (`lib/data.ts`) never uses `Intl`'s `style: "currency"` at all, only `style: "decimal"` for the number, with `currencyMap[currency].symbol` prepended manually (sign handled separately so negatives read `-$12.34`, not `$-12.34`). `"OTHER"`'s symbol is `""`, so this naturally prints a bare number with no prefix for it — no special-casing needed in `formatCurrency` itself, though `components/currency-picker-sheet.tsx` does skip the `(symbol)` suffix for it (every other row is `"{label} ({symbol})"`) since empty parens would look broken. `lib/use-currency.tsx` is a `CurrencyProvider`/`useCurrency()` Context (same reasoning as `AuthProvider`: many components format money, so one shared subscription beats each mounting its own listener on the same doc), scoped to `/users/{uid}/settings/preferences` → `{ currency }`, wrapped around `AppShell` in `app/layout.tsx` (inside `AuthProvider`, since it needs `useAuth()`'s `user`). Every component that calls `formatCurrency` or shows a currency symbol calls `useCurrency()` itself rather than receiving `currency` as a threaded-down prop — that includes `dashboard.tsx`'s local `BudgetCard` — consistent with how `useAuth()` is already called directly wherever needed rather than prop-drilled.

Changed from Settings (`app/settings/page.tsx`) via `components/currency-picker-sheet.tsx` — a bottom sheet listing all `currencies` (name + symbol in parens, current selection checked — including "Other", which renders as literal empty parens `()` rather than being hidden, showing there's genuinely nothing there instead of omitting the row's usual structure), opened by a small button showing just the current symbol with **no text fallback** — selecting "Other" leaves the button showing nothing but its chevron, which is the point (the word "Other" never appears on the trigger, only inside the sheet). That trigger button and the "Delete account" button in the row below share the same `min-w-20` (a floor, not a fixed width — either can still grow past it if its content ever needs more room) plus identical padding/text-size/centering, so the two rows' right-hand controls line up; the floor still matters since a bare `$` is much narrower than other symbols, and letting the pill shrink-to-fit made it visibly resize as the selection changed. **Deliberately not a native `<select>`** — an earlier version used one, but a native select's open dropdown can't be restyled away from the browser/OS's own default appearance (white background, system font, no dark-theme support), which looked out of place; a native `<select>` also needs `text-base` (16px) to avoid iOS Safari's focus-zoom, which made it visually mismatched in height against its sibling row's `text-xs` "Delete" button. The sheet-based picker sidesteps both problems — full control over styling since it's just app markup, and the trigger is a plain button that can stay `text-xs` like everything else in that row, since a button doesn't trigger the zoom behavior a real form field does. The amount inputs in `add-transaction-sheet.tsx` and `add-budget-sheet.tsx` show `currencyMap[currency].symbol` instead of a hardcoded `€` (see the Budgets section below for how that's positioned).

### Shared UI pieces

- `components/sheet.tsx` — **the app's one modal/bottom-sheet shell.** Every dialog in the app (`add-transaction-sheet.tsx`, `add-budget-sheet.tsx`, `budget-detail-sheet.tsx`, `currency-picker-sheet.tsx`, `confirm-dialog.tsx`, `delete-account-dialog.tsx`) renders through `<Sheet>` rather than hand-rolling its own overlay — it owns the backdrop (click to close), the slide-up rounded container, the drag-handle bar, Escape-to-close, and body-scroll-lock while open; each caller supplies only its header/body/footer as children. This exists because those six used to each hand-roll the same markup independently, and it quietly drifted: only the two add/edit sheets had Escape-to-close and scroll-lock, the other four had neither (though all six already closed on backdrop click, since that part happened to get copy-pasted consistently). Configurable per caller: `maxWidth` (`max-w-md` default, `max-w-sm` for the shorter confirm/picker dialogs), `scrollable` (adds `max-h-[80vh] flex flex-col` for a sheet with a long list body — `budget-detail-sheet.tsx`, `currency-picker-sheet.tsx`), `role` (`"alertdialog"` for confirm/destructive dialogs vs the default `"dialog"`), and `zIndex` (`confirm-dialog.tsx` uses `z-[60]` since it can stack on top of an already-open sheet, e.g. deleting a transaction from within `budget-detail-sheet.tsx`).
- `components/sheet-header.tsx` — the title + close (X) button row every sheet uses right after `<Sheet>`'s opening tag. Extracted once four sheets had it duplicated with a stray inconsistency (two used `mb-5`, two used `mb-4`) — this pins it to one value. Takes a `capitalize` flag for `add-transaction-sheet.tsx`'s heading specifically, which is built as `` `${verb} ${txType}` `` (e.g. "Add expense") and needs the second word capitalized too.
- `components/amount-input.tsx` — the big centered euro-sign-plus-number field shared by `add-transaction-sheet.tsx` and `add-budget-sheet.tsx` (was duplicated identically, comment included, before being pulled out). Reads the current currency itself via `useCurrency()` rather than taking it as a prop.

`Sheet` also tracks a module-level `openStack` (ids from `useId()`, pushed/popped as each instance's `open` prop goes true/false) so that when two sheets are stacked, **Escape only closes the topmost one** — the same as clicking outside already does, but for a different reason: a backdrop click only ever reaches the front sheet naturally (its full-screen backdrop physically covers whatever's behind it), while Escape is a single global `keydown` that every currently-open sheet's listener receives regardless of stacking, so without this check the *back* sheet would close first on the first Escape press (a real bug that shipped briefly) rather than the front one.
- `components/confirm-dialog.tsx` — the app's only confirm pattern for destructive-but-not-catastrophic actions (deleting a single transaction, deleting a budget). Built once and reused rather than duplicating the modal markup at each call site (each caller owns its own `open`/target state and passes in a title + description); native `confirm()`/`alert()` are avoided everywhere — they look and behave inconsistently on mobile and don't match the app's design. `components/delete-account-dialog.tsx` (Settings) is deliberately **not** built on `ConfirmDialog` — account deletion needed a heavier, type-"delete"-to-confirm flow, different enough from a plain yes/no that reusing it would have meant bolting extra props onto a shared component for one special case. Both still go through `Sheet` for their actual shell, just with different content.
- `components/empty-state.tsx` — the shared "nothing here yet" box (monochrome card, bordered, a colored icon in a circle, instructional text below). Used by `page-placeholder.tsx` (Insights), `app/budgets/page.tsx`'s empty list, and `components/dashboard.tsx`'s empty-budgets state, so all three read as the same pattern rather than three hand-rolled variants.

### Dashboard (`components/dashboard.tsx`)

Built around net worth rather than a spending list: header (month label only — an earlier version also had a small avatar circle with the user's initial, removed as clutter), then one row holding "Net" (this month's income minus expenses, the hero number, `items-end`-aligned against the two smaller figures beside it) with "Spent" and "Earned" to its right — all three in one horizontal row, each with its label stacked above its amount, not the whole trio stacked as separate rows, with `gap-8` between them (bumped up from `gap-5` — tighter spacing read as cramped next to the large "Net" figure). Below that, stacked budget cards (one per budget from `lib/use-budgets.ts`, largest amount first) under a plain "Budgets" label — **not a link**; navigation to `/budgets` happens only through the main nav and, when the list is empty, the empty state's inline link (see below), not a second in-page control that would duplicate it. There is deliberately **no transaction list on the dashboard itself** — tapping a budget card opens `components/budget-detail-sheet.tsx`, a bottom sheet listing that budget's matching transactions, each with edit (pencil) and delete (trash) icons. A budget card's progress bar is `--accent` normally; if `spent > amount` it switches to `--danger` and fills to 100% regardless of how far over. The empty-budgets state uses `components/empty-state.tsx`; only the word "Budgets" inside the sentence is a link, styled bold white (`font-bold text-foreground`) with **no underline** — clickability is signaled instead by `hover:scale-110` (the word grows slightly on hover), since underline-on-hover was deliberately dropped in favor of that.

"Spent" is computed differently depending on a budget's `cadence`, both derived client-side in `components/dashboard.tsx` (`spentByBudget`) — **monthly** budgets sum only this calendar month's matching expenses (resets every month); **one-time** budgets sum *all* matching expenses ever (a running total that never resets, since a one-time budget represents a fixed target rather than a recurring monthly cap). The same distinction carries into `budget-detail-sheet.tsx`'s transaction list — current month only for monthly budgets, all-time for one-time ones.

The FAB opens `components/add-transaction-sheet.tsx`, which has an Expense/Income toggle at the top — **only when adding**; when editing (`editing` prop set) the toggle is gone with nothing in its place (an earlier version showed a static "Expense"/"Income" label there instead, but that read as redundant clutter — the amount and description are enough context), since a transaction's type can't be changed after creation (switching an expense to income would need to somehow reattach or strand its `budgetId`, which is confusing either way — simplest to just not allow it). For Expense, budget pills are generated dynamically from the user's actual budgets (`budgets` prop, passed down from `components/dashboard.tsx`'s `useBudgets`) — tapping one sets `budgetId`, tapping the already-selected one again clears it (an expense with no budget is valid; there's no explicit "None" pill). If the user has no budgets yet, the whole budget-picker section is hidden rather than shown empty. The same sheet component handles both adding and editing: an `editing: Transaction | null` prop pre-fills the form and switches `onAdd` to `onUpdate` on submit; `components/dashboard.tsx` opens it in edit mode from the budget detail sheet's pencil icon.

`components/budget-detail-sheet.tsx` also shows the same spent/limit text + progress bar treatment as the dashboard's budget cards, right below the title — it sums the `transactions` prop it's given (already scoped to the right window by the caller) rather than taking a separate `spent` prop, since that sum is the same number the card already computed.

### Budgets (`app/budgets/page.tsx`)

Where budgets are actually created/edited/deleted (the dashboard only reads and displays them). A quiet, outline-style "Add budget" button (`border-accent/40 text-accent`, not a solid fill — deliberately less loud than the dashboard's solid-accent FAB) opens `components/add-budget-sheet.tsx`, which asks for amount, name, and cadence ("Monthly budget" / "One-time budget"). The cadence control is a small binary switch (`role="switch"`, a 36×20px pill track with a sliding thumb — the thumb needs an explicit `left-0.5` anchor plus a `translate-x` for the slide, **not** just a bare `translate-x` with no `left` set, which left it relying on the browser's implicit static-position fallback and made it render outside the track), not a wide segmented-pill toggle like Expense/Income in the transaction sheet — deliberately kept quiet/low-emphasis since it's a secondary setting, not the primary decision on the form the way expense-vs-income is. Doubles as the edit form via an `editing: Budget | null` prop, same pattern as `add-transaction-sheet.tsx`. Both this sheet's and `add-transaction-sheet.tsx`'s big amount input position the currency symbol (`currencyMap[currency].symbol` — was a hardcoded `€` before multi-currency support) absolutely (`right-full` of the input, not inline before it in the flex row) specifically so the *input* is what gets centered in the row — with the symbol inline, its width throws the centered typed number off-center. This holds regardless of symbol width (`$`, `CHF`, `R$`, …), which is why it's `right-full`-positioned rather than a fixed offset. The budgets list itself is sorted largest-to-smallest by amount; each row has the name, cadence, amount, and edit/delete icons (delete goes through `components/confirm-dialog.tsx`), plus a thin fixed-accent-color line underneath every row — **not** proportional to amount, purely decorative, identical on every row regardless of size (an earlier version varied its width by amount, which read as a meter and was confusing since nothing about it was actually fillable — dropped for exactly that reason). Empty state uses `components/empty-state.tsx` with the `Wallet` icon (same icon as the Budgets nav item).

### Styling

Tailwind v4 theme tokens are defined in `app/globals.css` via CSS variables + `@theme inline`: `background`, `foreground`, `accent`, `detail`, `muted`, `border`, `border-strong`, `card`, `surface`, `radius-card`. Use these token names (`bg-card`, `text-detail`, etc.) rather than raw hex values or ad hoc colors.

Any `<input>`/`<textarea>`/`<select>` needs `text-base` (16px) or larger — iOS Safari auto-zooms the page on focus if a form field's font size is under 16px. There's no global guard against this (a blanket CSS rule would also shrink the intentionally-large amount input in `add-transaction-sheet.tsx`), so it has to be applied per-field.

### Path alias

`@/*` maps to the repo root (see `tsconfig.json`), e.g. `@/lib/data`, `@/components/dashboard`.

### Environment

Firebase web config lives in `.env.local` as `NEXT_PUBLIC_FIREBASE_*` variables (gitignored, required for `lib/firebase.ts` to initialize). `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is the OAuth Web client ID Firebase auto-created for the Google sign-in provider (same value visible in Firebase console → Authentication → Sign-in method → Google, or Google Cloud Console → Credentials) — required by `AppShell`'s Google Identity Services setup.

**Setup gotcha:** GIS separately requires every origin it'll run from (`http://localhost:3000`, the deployed Vercel domain, etc.) to be listed under that same OAuth Client ID's **"Authorized JavaScript origins"** in Google Cloud Console (APIs & Services → Credentials — a direct link like `https://console.cloud.google.com/apis/credentials?project=<firebase-project-id>` gets there fastest). This is a *different* setting from Firebase's own "Authorized domains" list (Authentication → Settings) — missing it produces a real Google-hosted "Access blocked: Authorisation error" page, not a console warning, so it's easy to mistake for something more exotic if you don't know to look here first.
